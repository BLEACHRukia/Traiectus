# Traiectus tray launcher - manual

Folder: `<project folder>\launcher\`

> This is the English version of `说明.md` (same content, same behaviour).
> The UI it describes has a language menu: **Language → 中文 / English**.

---

## 1. What this is

The Windows side used to be "server and bridge, each started by hand".
This is a single manual entry point instead.

- Start it -> the server comes up
- Click "Quit" -> the server, the watchdog, the ports and the cursor lock are
  **all cleaned up at once**
- Tray icon: **grey** = stopped, **green** = running, **red** = error

There is deliberately **no "stop" state in between** - while it runs you can only
"Restart" or "Quit", so the state is never ambiguous.

It does **not** auto-start and does **not** register a Windows service. Start it
when you want it, quit when you do not - that way the machine is completely clean
before you launch a game.

It only does three things: start the child processes, show the tray state, and
clean them up on exit. It never touches an input device - no hooks, no
interception, no injection, no drivers.

Chinese one and writes a line to `Traiectus-Launcher.log`. An existing
`config.ini` is **never** rewritten.

## 3. How to use it

### Option 1 (recommended): run it straight from the project folder

1. Double-click `build-launcher.bat` -> produces `launcher\Traiectus.exe`
2. Right-click `建桌面快捷方式.ps1` -> Run with PowerShell -> a `Traiectus`
   shortcut appears on the desktop
3. Double-click `Traiectus` on the desktop

The launcher finds `..\phase3-tcp\build\Traiectus-Server.exe` by itself - there
is **nothing to install**. Its log goes to `launcher\Traiectus-Server.log`
(see section 7).

This is the most robust option: the exe lives inside the project folder, so the
path can never break because of redirection.

### How the Mac finds this PC

**You do not have to type an IP - it discovers by itself:** the server waits for
one broadcast on UDP 45791 - the Mac shouts `WHO 1`, the server unicasts back
`HERE 1 45789` (telling it the TCP port). So on the Mac you just click "Connect";
it tries the address it remembers first, then broadcasts. (This reply does not
depend on any client connection, so it works on a brand-new install too.)

### Option 2: install into %LOCALAPPDATA%\Traiectus

Double-click `安装 Traiectus.bat` -> installs into `%LOCALAPPDATA%\Traiectus\`
and creates a desktop shortcut.

⚠️ **You have to double-click this one yourself.** See the last item in section 8
for why.

The installer also removes an old background bridge auto-start (a
`TraiectusBridge.lnk` in the Startup folder) left behind by earlier versions, so
an old config cannot fight the new one.

### Day to day

- Double-click `Traiectus` on the desktop -> a grey dot appears in the tray and
  turns green within a few seconds, meaning the server is up
- Done -> right-click the tray dot -> **Quit**

### Uninstalling

- Option 1: delete the desktop shortcut, and delete the `.log` files the launcher
  generated inside `launcher\`
- Option 2: double-click `卸载 Traiectus.bat`

Neither touches the registry, services, drivers or the firewall.

## 4. The right-click menu

```
Status: running                    <- the next few lines are grey status text
This PC: 192.168.1.20
Mouse switching: Ctrl+Alt+M ✓
Mouse: VID_xxxx&PID_xxxx&MI_00 ✓
------------------------
Set mouse-switch hotkey            <- see "Changing the hotkey" below
Detect mouse                       <- re-run detection (see "Mouse device")
------------------------
Restart                            <- only shown while running
Re-pair                            <- see below
Open log folder
------------------------
Language  ->  中文 / English        <- takes effect immediately, saved to config.ini
------------------------
Quit
```

While stopped, the "Restart" row becomes "Start Traiectus".

"**This PC**" is the IPv4 address of the interface that currently holds the
default route (it never shows a Tailscale or virtual adapter address) and it is
queried fresh every time you open the menu - that one line is enough to check
which address the Mac should connect to. On start-up the server also logs a fuller
line: `本机网络：WLAN 192.168.1.20 网关 192.168.1.1 DHCP租约 过期 …`.

### Language / Language

Click **中文** or **English** and the menu and the tooltip change immediately -
the process is not restarted. The choice is written back to `config.ini`
(`[ui] language=`), so it survives a restart of the launcher and of Windows.

Which language is used, in order of priority:

1. `--lang zh|en` on the command line (this run only; it is not written back)
2. `[ui] language=` in `config.ini`
3. otherwise: the Windows UI language - Chinese Windows gives Chinese,
   anything else gives English

The choice is also passed on to the server (`--lang`), so the pairing dialog,
the `--show` window, `--help` and `--list` follow the same language.
The **logs stay Chinese** in both languages - the tray reads machine-readable
lines such as `:45789`, `DEVICE …` and `HOTKEY …` out of the server log.

### About "Set mouse-switch hotkey"

Clicking it opens a small window: **press the combination you want**, the window
shows what it captured, and "Save" writes it back to `config.ini`'s `--hotkey`
and restarts the server automatically (a few seconds; the Mac blinks and
reconnects by itself).

Rules:

| Action | Behaviour |
|---|---|
| Press a combination | Shown immediately; the window states the supported range: modifiers Ctrl / Alt / Shift / Win (at least one), main key A-Z / 0-9 / F1-F24 |
| Main key only, no modifier | "At least one modifier is required"; **Save is greyed out** (a bare key registered globally destroys normal typing) |
| `Esc` | Close, change nothing |
| `Delete` / `Backspace` | Clear = save as `off` (no hotkey); the menu then shows "Mouse switching: not set" |
| Save | Edits that one line of `config.ini` in place - **not a single byte of any other line changes** - then restarts the server |

The first menu line shows **whether registration actually succeeded** (it reads
the status line out of the server log):

```
Status: running   Mouse switching: Ctrl+Shift+M ✓              <- registered
Status: running   Mouse switching: Ctrl+Shift+M ✗ taken by another app
                                                               (log has HOTKEY FAIL … 1409)
Status: running   Mouse switching: not set                     <- saved as off
```

⚠️ **A successful registration means this combination is reserved system-wide by
this app** - no other program (including games) can get it. So do not pick a
shortcut you actually use elsewhere.

### About the mouse device ("Detect mouse")

**Normally you do not have to configure anything.** As long as `config.ini`'s
`args` contains **no `--device`** (the template leaves it out), the server
watches for **8 seconds** after start:

    "whichever device really produces mouse events during that window
     is the mouse you are using."

It does not rely on enumerating devices - that list is full of virtual devices,
the receiver's second interface and touchpads, and users simply pick the wrong
one; **"who is actually moving" is the only reliable signal**. When the window
ends it prints a line `DEVICE PICK <device string>`, the launcher writes it back
to `config.ini` and restarts once, and from then on only that mouse is forwarded.

The menu's second line shows the current state:

| Shown | Meaning |
|---|---|
| `Mouse: VID_xxxx&PID_xxxx&MI_00 ✓` | Fine - that is the mouse |
| `Mouse: all (not specified)` | No device string configured = every mouse-class device is forwarded |
| `Mouse: ✗ no match (new mouse? click "Detect mouse")` | None of the configured string's events matched (new mouse / different port) |
| `Mouse: 3 found → click "Detect mouse" to pick one` | Several devices moved; you have to pick one |
| `Mouse: none found → click "Detect mouse" to retry` | Nothing moved during those 8 seconds |

**Changed mouse?** Click "**Detect mouse**" - the server re-detects for 8 seconds:

- only one device moved -> locked in immediately, written back to the config
- **several devices moved (e.g. the laptop trackpad too) -> a small window lists
  the candidates and you pick one**, it does not guess
- nothing moved -> you are told to retry

Also: if the configured string **keeps dropping events** (mouse changed but the
config was not updated), the server prints `DEVICE MISS <string>` after 10
seconds and **re-detects automatically once** - so changing the mouse needs no
config edit, moving it for a moment is enough to recover.

> ⚠️ After editing `config.ini` by hand you must **restart the tray** for it to
> take effect (the tray reads the config once, at start-up). Changing it through
> "Detect mouse" / "Set mouse-switch hotkey" does not need that - those restart
> the server themselves.

### About "Re-pair"

All it does is **delete the pairing file** (by default
`phase3-tcp\paired.json`; if you put `--pair-file` into the config's `args`, then
that path). The server does not cache the token - it reads the file at handshake
time - so after deleting it **the Mac is asked again the next time it connects**.
The currently connected session is not affected. Clicking it first shows a
confirmation dialog that names the exact file.

The pairing file is the only source of the token (the `--token` option was
removed on 2026-10-01), so **this item is always clickable** and its only action
is "delete that file".

## 5. What "Quit" cleans up

| Cleaned up | How |
|---|---|
| Server `Traiectus-Server.exe` | Job Object |
| Bridge `powershell + TraiectusBridge.ps1` (**retired, not started by default**) | Job Object |
| The watchdog process the server started | Job Object (goes with it) |
| Ports 45789 / 45790 / 45791 | The processes are gone, so the ports are released (45789 TCP mouse events, 45790 UDP key head-start frames, 45791 UDP address discovery) |
| Cursor lock | The launcher calls `ClipCursor(NULL)` itself as a backstop |
| Tray icon | Removed explicitly |

**The Job Object is the core of it**: the launcher creates a Job with
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and puts its child processes in it. The
moment the launcher disappears (normal exit, force-killed, crashed) the kernel
kills every process in the Job **including grandchildren**. That is far more
reliable than killing them one by one with `taskkill`, and it cannot miss the
watchdog.

## 6. Implementation notes (deliberate design choices)

This section explains the places that look odd but are on purpose. Read it
before changing the code.

### 6.1 `#include` order: winsock2.h must come before windows.h

The other way round, windows.h pulls in the old winsock.h first and then
winsock2.h, which produces a screenful of redefinition errors.

### 6.2 Deciding "is the server up": read the log, do not connect to the port

The obvious approach is to open a TCP connection to `127.0.0.1:45789` to probe
it. But the server **serves exactly one client at a time, and a new connection
unconditionally kicks out the old one**, so that probe could disconnect the Mac.

So instead the launcher **only reads the server's own log**: after a successful
`listen()` the server prints `监听 0.0.0.0:45789（TCP）`, and the launcher looks
for the ASCII substring `:45789` in that file. It never touches the port.

### 6.3 The build must use `-static`

Without it the exe depends on `libstdc++-6.dll` / `libgcc_s_seh-1.dll`, and once
`安装 Traiectus.bat` copies it into `%LOCALAPPDATA%\Traiectus\` a double-click
fails with a "missing DLL" dialog.

`build-launcher.bat` already passes `-static -static-libgcc -static-libstdc++`;
the resulting exe depends only on 6 system DLLs (KERNEL32 / USER32 / GDI32 /
SHELL32 / WS2_32 / msvcrt).

### 6.4 The program finds its own files

It looks next to the exe first, then tries `..\phase3-tcp\build\` and `..\`.
That way **the same config.ini** works both in the development folder and in the
install folder.

### 6.5 The single-instance mutex is session-local, not `Global\`

The `Global\` namespace can fail to create for an ordinary user process, and a
tray program is one per logon session anyway. Creation is NULL-checked.

### 6.6 The bridge log is two files

The bridge writes its own `-OutFile TraiectusBridge.log`, and the launcher
redirects the bridge's stdout/stderr to `TraiectusBridge-console.log`. Sharing
one file would make two writers fight over it.

### 6.7 Health check: all on, or all off

If it only did "server died -> tray goes red" and stopped there, we measured
three problems:

1. the bridge becomes an **unmanaged stray process**, still sending UDP to the Mac;
2. clicking "Start Traiectus" then starts **a second bridge** - two bridges
   sending UDP at the same time;
3. the old Job handle is overwritten and leaks.

So now: **if either child exits, the other part is cleaned up too** - there is no
"half alive" state, and `StartServices()` clears leftovers from the previous
round before starting anything.

Same idea as "no intermediate stop state": either everything is on, or
everything is off.

### 6.8 Why the `.bat` files are in English

Every `.bat` in this folder contains **pure ASCII**. Reason: cmd.exe reads the
bytes of a `.bat` file using the local OEM code page, so Chinese text gets
decoded as garbage and the script dies with a stream of
`'xxx' is not recognized`. `chcp 65001` plus Chinese `echo` is not reliable, so
the scripts are plain English and the Chinese documentation lives in the `.md`
files.

## 7. Logs

They live in **the folder the launcher runs from** (on this machine
`<project>\launcher\`; if it was installed it is `%LOCALAPPDATA%\Traiectus\` -
whatever folder holds the launcher):

| File | Content |
|---|---|
| `Traiectus-Server.log` | **The only active log**: everything the server prints. Truncated on every start, so it only reflects the current run |
| `Traiectus-Launcher.log` | Only used for rare notes that do not fit in a dialog (e.g. "the English template is missing, falling back to the Chinese one") |
| `TraiectusBridge-console.log` | Historic file (stops being updated once the keyboard frames moved into the server and the bridge was retired) |
| `TraiectusBridge.log` | Same, historic; only written again if you temporarily start the bridge for A/B comparison |

The names come from `[server] log=` / `[bridge] log=` in `config.ini`.

The tray's "Open log folder" opens that folder directly. If the server start
times out, a dialog tells you where to look.

## 8. Troubleshooting

### The tray stays grey and never turns green

The server did not start. Look at `Traiectus-Server.log`; double-clicking
`Traiectus` also pops up a dialog with the reason. The most common cause is a
missing `phase3-tcp\build\Traiectus-Server.exe` (run
`phase3-tcp\build-mingw.bat` first).

### The tray turns red

A child process exited. Hovering over the dot says whether it was "the server has
exited" or "the bridge has exited". Right-click -> Start Traiectus brings it back.

### Double-clicking Traiectus does nothing

It is probably already running. Another double-click only pops up the menu; it
does not start a second process (by design).

### The pointer is invisible (you can click and move, but cannot see it)

**First work out whose problem it is** - this project's lock can only make the
cursor *stop moving*; it never makes it *invisible*:

```powershell
# 1) The system cursor clip area: full screen = not locked; 1x1 = locked (Mac mode)
# 2) Whether the files the cursor scheme points at actually exist
Get-ItemProperty "HKCU:\Control Panel\Cursors" | Select-Object '(default)', Arrow
```

- **Clip area is full screen and the tray's first line is not Mac mode** ->
  **it is not this project.** Seen on real hardware on 2026-10-07: the desktop
  theme (`Custom.theme`) pointed all 15 cursors at
  `C:\WINDOWS\Resources\Themes\Golden Gate\Cursors\`, and **that folder does not
  exist** - the pointer had no image to draw, so it could be clicked but not seen.
  Fix: Settings -> Bluetooth & devices -> Mouse -> Additional mouse settings ->
  **Pointers** -> pick a scheme -> Apply. Also fix those lines inside the `.theme`
  file, or applying that theme breaks it again.
- **The tray's first line says Mac mode and the cursor will not move** -> that is
  this project's lock; press `Ctrl+Alt+M` to switch back.

### Where do I change the token or the device?

In `config.ini`, under `server.args`. After editing, either double-click
`安装 Traiectus.bat` again to copy the new config into the install folder, or
edit `%LOCALAPPDATA%\Traiectus\config.ini` directly.

**There is no token to fill in** - that option is gone (`--token` was removed).
Windows generates the token during pairing and stores it in
`phase3-tcp\paired.json`; the Mac remembers it. Neither machine needs typing.
What you may want to change is `--device` (the mouse device string) and the port.

### What is that dialog on Windows the first time a Mac connects?

That is the **pairing confirmation** (it only appears when this Mac has not been
paired yet; it will not bother you again). It is modelled on a macOS permission
sheet - a rounded, **title-bar-less** panel with two lines:

```

        A Mac wants to connect to this PC

                [ Allow ]  [ Deny ]
```

- "**Allow**" -> a token is generated, the Mac remembers it and connects
  automatically from then on
- "Deny" / Enter / Esc all count as a refusal (the default button is Deny too)
- **60 seconds of inactivity = automatic denial** (`--pair-timeout <sec>` changes
  it; 30 seconds used to be too short - in practice you have to click Connect on
  the other machine and switch the monitor input first)
- Changed your mind? Tray right-click -> "Re-pair" deletes the pairing file, and
  the Mac is asked again the next time it connects

The layout is computed from real font metrics (not hard-coded pixels): body text
13pt, buttons 12pt (108x34), the window width follows the content
(`max(text width, button row width) + 28 px side padding`, clamped to 380..480),
the text row's box height is the font's real line height, and the top padding
(28) is slightly larger than the bottom (26) - because that line has no
descenders, so its optical centre sits high and equal padding looks "stuck to the
top".

### Windows says it is already paired, the Mac says it cannot connect (`already-paired`)

This means: **Windows has a pairing file (a token exists) but the Mac does not
have that token** (reinstalled, different machine, or you cleared it in the Mac
UI). The Mac then asks to pair, and Windows refuses by design (so a stranger
cannot displace an existing pairing), leaving the Mac stuck at "this Windows is
already paired".

**The Mac cannot fix this on its own.** There is exactly one way out, on the
Windows machine: tray right-click -> "Re-pair" -> confirm -> back on the Mac
click "Connect" -> click "Allow" in the dialog. The Mac no longer has any
"type the token by hand" box, so this is the only route.

### Double-clicking the desktop Traiectus does nothing / says the file is missing

The shortcut points at an exe that is no longer there. In the `launcher` folder,
right-click `建桌面快捷方式.ps1` -> Run with PowerShell, and it re-points the
shortcut at the `Traiectus.exe` in that folder.

### Changed IP, or the "head start" stopped working?

(What "head start" means: when you switch to the Mac on the keyboard, the Mac
switches its screen over **early**, saving the second or so of waiting. It works
because the server forwards the keyboard receiver's status frames to the Mac.)

**If this Windows machine runs a proxy** (Clash / v2rayN / Surge / any TUN
mode), the proxy may **swallow packets destined for the LAN** - without reporting
any error at all:

| Proxy mode | Effect on Traiectus |
|---|---|
| System proxy only (HTTP / SOCKS) | **No effect** - the server sends UDP on a plain socket, and WinSock ignores the system proxy settings |
| TUN / virtual adapter mode | **Risky** - it captures at the IP layer and routes by rule; if "LAN direct" is not covered, the packets are gone |

When that happens the Mac **quietly loses three things**:

- the `HB` heartbeat and the `HERE` reply -> the Mac cannot learn the address
  (it falls back to broadcasting/scanning: slower, but it still connects)
- **the `KEY` status frames -> no head start, the screen takes a second longer to
  switch** (the easiest to notice, the hardest to diagnose)

**How to tell**: look in the **Mac client's** log for lines like
`⚡ Windows 抢跑：键盘正在…`. **Absent = the frames never arrived = no head start.**

**How to fix it**: in your proxy software, make the **private ranges direct /
bypassed**: `192.168.x.x`, `10.x.x.x`, `172.16~31.x.x`, plus the broadcast
address `224.0.0.0/4`. Most setups have this by default; you only need to check
if you customised the routing rules.

> This is not specific to Traiectus - any LAN-based KVM / screen sharing /
> streaming tool needs "LAN direct". A proxy should only proxy traffic that
> leaves the network.

### The log shows "client connected…" and 3 seconds later "no data from the peer for 3 seconds"

**This is usually not a fault - it is the Mac discovering the address.**

The last layer of the Mac's "find Windows" is **scanning its own subnet**
(254 addresses), knocking on TCP port 45789 one by one. The server accepts only
one client at a time, so those probes briefly squeeze the connection - which is
exactly those two log lines.

In normal use you can ignore it (once the scan finishes it connects to the real
one). The only case worth noting: **if a second Mac is connected to this Windows
machine at the same time**, a scan from the other one displaces it (it will
reconnect automatically). Single-user setups never see this.

### ⚠️ Why you must double-click the installer yourself

`安装 Traiectus.bat` writes files into `%LOCALAPPDATA%\Traiectus\`.

If something else runs it for you - for example a sandboxed or containerised
coding assistant - that assistant may redirect `%LOCALAPPDATA%` into its own
container, e.g.

    ...\Packages\<app>\LocalCache\Local\Traiectus\

The result is that **the files are installed (into the container's copy) but the
desktop shortcut points somewhere that does not exist from your point of view,
so double-clicking does nothing**.

So:

- installing / uninstalling anything under `%LOCALAPPDATA%` -> **you double-click it yourself**
- anything inside the project folder (`<project folder>\...`) -> no such problem,
  anyone can run it

That is also why "Option 1" above is the recommended one: it never uses
`%LOCALAPPDATA%` at all.

## 9. Processes and memory

Running normally (Windows mode) there are **2 processes**:

    Name                     Memory    Notes
    Traiectus.exe             ~10 MB    Launcher (tray)
    └─ Traiectus-Server.exe    ~7 MB    Server

Pressing Ctrl+Alt+M to enter Mac mode adds **one more** (it disappears when you
switch back, it does not accumulate):

    Traiectus-Server.exe --watchdog <main pid>   ~7 MB   backstop: releases the
                                                         cursor lock within 200 ms
                                                         if the main process is killed

### About conhost

Windows gives every "console subsystem" program a `conhost.exe` host process -
**even if its window is invisible**. The server only prints to a redirected file
and needs no console, so it is created with **`DETACHED_PROCESS`** instead of
`CREATE_NO_WINDOW`, which saves one conhost.

> A trap we hit along the way: the old bridge was `powershell.exe`, which
> **does** need a console. Starting it with `DETACHED_PROCESS` produced no output
> at all, a 0-byte `TraiectusBridge-console.log`, and an instantly disappearing
> process; one second later the health check declared "the bridge has exited" and
> - following the "no half states" rule - cleaned the server up as well. It
> looked like "the server crashed by itself", but the Windows event log showed
> **no crash, just a normal exit**: the signature of being collected by the Job.
>
> So the rule is: the server -> `DETACHED_PROCESS`; anything that needs a console
> -> `CREATE_NO_WINDOW`.

### About "cleaned up"

Tray right-click -> "Quit" cleans up the server, the watchdog, the ports and the
cursor lock in one go (see section 5). **There is no Windows service, no
auto-start entry and nothing left running in the background.** Quit it before
you play and nothing of it remains on the system.

## 10. Safety statement

The launcher itself **never touches** any input device:

- no hooks, no interception, no injection, no drivers
- no service, no auto-start, no registry changes
- no firewall changes (the rules that are needed stay the job of
  `windows/control-channel/Traiectus-firewall.ps1` - inbound must be allowed for **TCP 45789** and
  **UDP 45791** (address discovery); UDP 45790 is sent *by* the server and its replies come back to
  an ephemeral port, so it needs no rule)

It does three things: start two processes, show the tray state, and clean them up
on exit.
