# 架构与设计理由

这份文档回答"每个机制为什么这么设计"。协议细节见 [`../PROTOCOL.md`](../PROTOCOL.md)，
过程与实测数据见 [`devlog/`](devlog)。

---

## 1. 组件

| 组件 | 在哪 | 职责 |
|---|---|---|
| **Traiectus Client** | Mac（SwiftUI 菜单栏 app） | 连 Windows、注入鼠标事件、键盘联动、睡眠交接、睡眠热键 |
| **Traiectus Server** | Windows（C++ / Raw Input） | 只读捕获鼠标、按控制权转发、切控制权时锁定 Windows 光标 |
| **Traiectus Launcher** | Windows（托盘入口 `Traiectus.exe`） | 用户唯一的入口：拉起/重启服务端与看门狗、托盘状态三行、检测鼠标、设置鼠标切换快捷键、重新配对、语言切换、打开日志目录、退出 |
| **抢跑读帧**（3b 起做在服务端里） | Windows（C++，与鼠标转发同一个 exe） | 只读监听键盘接收器的状态帧 → UDP 通知 Mac"抢跑"。**原 PowerShell 桥接已退役**（职责并入服务端，分发时只需要一个 exe） |
| **kvm-keywatch** | Mac（C，IOKit） | 监听键盘设备在 Mac 上的出现/消失 —— 判断"键盘走了没有" |
| **m1ddc / dwc** | Mac（外部 CLI，随 app 打包） | 通过 DDC/CI 切显示器输入源 |
| **界面语言表** | Mac：`src/Localization.swift`（159 条）；Windows：`launcher/i18n.h`（113 条） | 中文原文 → English 的对照表；**只翻界面，日志保持中文**（排查时两端对得上更重要） |

**界面语言怎么生效**：Mac 在「设置 → 通用 → 语言」里切，**当场生效不重启**；Windows 侧三级优先
——`--lang` > `config.ini` 的 `[ui] language` > 系统 UI 语言（托盘里也能切，会写回 ini）。
两份表都是"查不到就回退显示中文原文"，宁可显示中文也不显示空白或 key。

**为什么键盘用"设备出现/消失"判断，而不是读键值**：
`Fn+Caps` / `Fn+T` 这类组合键是**键盘固件内部**处理的，主机根本收不到这个按键。
主机唯一能观察到的是"键盘这个 USB/蓝牙设备从我这消失了"。这个判断是**零权限、零 hook**的，
代价是只能知道"走了"，不知道"去哪了"。

## 2. 鼠标转发

```text
GPW2 ──2.4G──► Windows 服务端 ──TCP(局域网, 行协议)──► Mac 客户端 ──CGEvent──► 系统
                    │
                    └─ 只读 Raw Input：不拦截，Windows 本地鼠标照常工作
```

要点：

- **行协议**（`\n` 分帧）：一次 `recv` 可能拿到半行、一行或多行，`LineFramer` 负责切分与残包。
- **按住拖动**要发 `*.leftMouseDragged` 之类的拖拽事件 —— 一直发 `mouseMoved` 的话，
  系统只当"光标在动"，表现就是**拖不动窗口/文件**（这个 bug 真机上出现过一次）。
- **断开时补发抬起**：连接断了要 `releaseAllHeldButtons()`，否则按键卡住。
- **滚轮零头累积**：高分辨率滚轮会送来 `±1` 这种小值，累积够一格（120）才滚，否则完全滚不动。
- **用 HID 系统来源创建事件**：某些带自动化能力的 App 会看事件的来源 ID，
  非 HID 来源的合成事件可能被直接忽略。

## 3. 一次按键全切（键盘 → 屏幕 + 鼠标）

```text
你按 Fn+Caps
   │
   ├─ 键盘固件：切到 2.4G 主机（Windows）         ← 主机收不到这个按键
   │
   ├─ ① Windows 服务端：接收器吐出状态帧 00 00 01 36 00 02
   │       └─► UDP 45790 → Mac："键盘正在过去"      ← 比 Mac 自己发现早约 1.7 秒
   │
   └─ ② Mac 侧：蓝牙链路里键盘消失
           └─► kvm-keywatch 事件 → 确认键盘走了

Mac 收到 ① 或 ② 之后做三件事：切显示器输入源 → 光标移到屏幕中心 → 把鼠标控制权交给 Windows
```

**为什么要抢跑**：Mac 侧发现"键盘走了"只能等蓝牙链路真正断开 —— 实测比接收器的状态帧
**晚 1.56~1.82 秒**（而且**只对"去 Windows"方向有优势**："回 Mac"方向 2.4G 掉线和蓝牙重连
几乎同时发生，实测只早 0.13~0.28 秒，也就是那个方向本来就没有提前量）。
接收器在键盘一过来就吐帧，抢跑把这 1.7 秒抹掉了。

> 早期这段读帧逻辑放在一个独立的 PowerShell 桥接里；**3b 起已并入服务端**
> （只读、按 usagePage/usage 枚举、不写死 DevicePath），分发时只需要一个 exe。
>
> 顺带一条实测结论：**鼠标控制权切换（`MODE`）一直走 TCP 协议行**，
> 从来没走过 UDP 45791 —— 早期那条"桥接把 Mac 的 UDP 回包中继到 45791"其实是多余的。

**为什么切屏前要把光标移到屏幕中心**：切输入源时鼠标控制权也在换手，
不重新关联的话光标可能停在屏幕外或被系统解绑（`CGAssociateMouseAndMouseCursorPosition`）。

## 4. 睡眠交接

```text
按 ⌘1（全局热键，可在设置里改）
   └─► NSWorkspace.willSleepNotification
          ├─ 切显示器输入源到 Windows
          └─ MODE Win（把鼠标控制权交给 Windows）

系统真正睡下去 ≈ 4 秒后（这中间我们早就交接完了）

唤醒（按键盘任意键）
   └─► didWakeNotification → 等 1.5 秒让蓝牙归属判准
          ├─ 切回 HDMI（**不受"对端是否在线"限制** —— 唤醒瞬间 Windows 往往还没连上）
          └─ MODE Mac
```

**为什么不用"键盘离开 Mac"来触发睡眠交接**：Mac 睡下去会把键盘的蓝牙链路断掉，
联动会把这件事误判成"键盘走了"。靠这个副作用触发的话，交接要等 1.4 秒；
如果联动没开，则要等服务端发现客户端掉线，**卡 4~5 秒**。改成监听系统事件后是 0.19 秒。

**为什么睡眠期间"什么都不做"**：那段时间的键盘事件都是"Mac 睡过去了"的余波
（实测键盘还会短暂跳去 2.4G 再跳回来），只同步状态、不触发动作，
再加 60 秒看门狗和 3 秒唤醒宽限，避免 IOKit 补发的事件把屏幕刚醒就切走。

## 5. 为什么不 hook、不装驱动

设计红线（写在项目最开始，后面所有取舍都遵守）：

1. 不影响 Windows 正常鼠标输入 —— 所以**只读** Raw Input，不拦截
2. 不装驱动、不用内核扩展、不修改系统文件
3. 不改 G HUB / DPI / 鼠标固件 / 网络代理
4. 退出后 Windows 鼠标必须恢复原样（= 因为从未改变过）

唯一"越线"的地方是 **Windows 侧锁定光标**（切到 Mac 时用 `ClipCursor` 把 Windows 光标按住），
并且给它加了 200 ms 看门狗：即使进程被强杀，光标也会自动解锁。

## 6. 已知的架构边界

| 边界 | 说明 |
|---|---|
| 键盘换主机只能手动 | 那是键盘固件的事。除非键盘 USB 线插在 Mac 上，才能走厂商 HID 命令（`00 08 01 3A 00 <mode>`，K70 Pro Mini 实测可用） |
| Mac 必须"睡眠"不能关机 | app 得活着，Windows 起来后它才能自动重连 |
| DDC/CI 只对当前输入有效 | 屏幕在 DP 上时 Mac 看不到显示器，所以"切回 Mac"必须由当时在显示的那一端发起 |
| 显示器有没有"输入源自动检测"会影响观感 | 有的话"Mac 睡 → 画面自己过去"是它做的；没有就完全靠软件 |
| 鼠标坐标限制在主显示器内 | 反复撞边缘会累积偏移；边缘切换属于后续工作 |
