## 2026-09-24 · Phase 3 联调（Mac ↔ Windows，同一台设备的首次真机联调）

### 环境

| 项 | 值 |
|---|---|
| Mac | `192.168.1.10`，接口 `en1`（**Wi-Fi 2.4 GHz / 1 信道 / 20 MHz / 802.11n**；有线口 `en0` 未连接） |
| Windows | `192.168.1.20`，MiniKVM Server，端口 `45789` |
| 客户端 | MiniKVM Client（`com.minikvm.client`），已授权辅助功能 |
| 用户侧网络约束 | 不能走有线（会影响自建代理节点的接入），因此维持 2.4 GHz Wi-Fi |

### 测量 1：网络底噪（Windows 侧点名要求）

```text
$ ping -c 20 192.168.1.20
20 packets transmitted, 0 packets received, 100.0% packet loss
```

**这不是断网**：TCP 连接同期是 `ESTABLISHED` 且握手正常。是 **Windows 防火墙默认拦截 ICMP Echo**。
→ 结论：在这台 Windows 上**不能用 ping 测延迟**，除非放行 ICMP（属于修改防火墙规则，需用户明确同意）。

改为 ping 本机路由器（测 Wi-Fi 这一跳的底噪）：

```text
$ ping -c 20 192.168.1.1
20 packets transmitted, 20 packets received, 0.0% packet loss
round-trip min/avg/max/stddev = 2.852/7.186/12.353/3.306 ms
```

→ 2.4 GHz Wi-Fi 首跳：**平均 7.2 ms、最大 12.4 ms、抖动 ±3.3 ms**。不理想（有线通常 < 1 ms），
但**量级上解释不了 0–188 ms 的抖动**。

### 测量 2：代理/隧道是否影响局域网

```text
$ route -n get 192.168.1.20
  interface: en1                       ← 直连 Wi-Fi，没有走 utun
$ scutil --proxy
  ExceptionsList: 192.168.1.20        ← 局域网地址已在代理例外列表里
```

系统跑着本地代理（`127.0.0.1:10808`）和多张 `utun` 网卡，但到 Windows 的流量**直连**，未被接管。
→ 结论：**代理与隧道与本项目无关**。另：MiniKVM 全程只用局域网，不需要互联网。

### 测量 3：Mac 客户端自测（新增打点后）

客户端每 5 秒写一行统计到 `~/Library/Logs/MiniKVMClient.log`：

```text
[16:55:36.693] 统计 5 秒：收   2.0 行/秒 · 注入   0.0 事件/秒 · 往返(最近) 15.1 ms · 最大收包间隔 986.0 ms · 单行最长处理 0.03 ms
[16:55:41.693] 统计 5 秒：收   2.0 行/秒 · 注入   0.0 事件/秒 · 往返(最近) 10.5 ms · 最大收包间隔 787.1 ms · 单行最长处理 0.04 ms
```

（此时服务端处于 Windows 模式，不转发事件，所以"注入 0"、"收发包间隔 ≈ 心跳周期 1 s"都是正常的。）

→ **单行最长处理 0.03 ms**：客户端处理一行只要几十微秒，**它不是瓶颈**。
→ **客户端自测往返 10–15 ms**，与首跳 Wi-Fi 底噪（avg 7 ms / max 12 ms）量级一致。

### 关键对照：同一条往返，两端量出来差一个数量级

| 测量方 | 往返延迟 |
|---|---|
| Mac 客户端自测（PING→PONG） | **10–15 ms** |
| Windows 服务端自报 | **0–188 ms，近似均匀铺开** |

Windows 侧的样本为 `0 / 16 / 31 / 32 / 47 / 62 / 94 / 125 / 172 / 188`，
间隔基本是 **~15.6 ms 的倍数**——那是 Windows 计时器 tick 的颗粒度（`GetTickCount64`），
用这个时钟分辨不出 1 ms 与 15 ms。**基于它推出"客户端每 200 ms 轮询一次 socket"不可靠。**

### 定位结论：延迟在 Windows 服务端的发送循环，不在 Mac 客户端

服务端原代码：

```cpp
timeval timeout{0, 200000};                       // 固定 200 ms
const int ready = ::select(0, &readSet, haveClient ? &writeSet : nullptr, nullptr, &timeout);
```

写集合只在**循环开头队列非空**时才登记客户端 socket。于是主线程（Raw Input）刚塞进队列的鼠标事件，
必须**等满一轮 `select`（最多 200 ms）**才被送出去 —— 这单独就能造成
"事件成批送达 + 0–200 ms 均匀抖动"，与 Mac 侧完全无关。

**修复（已合入仓库）**：队列非空时用 1 ms 超时，空闲时仍用 200 ms。

```cpp
const bool pendingOutput = HasPendingOutput();
timeval timeout{0, pendingOutput ? 1000 : 200000};
```

## 2026-09-24 · 第二轮复测：服务端补丁后的实测（结论：定位确认，卡顿已消除）

### Windows 侧做了什么

1. **承认上轮结论方法论有误**：用 `GetTickCount64`（~15.6 ms 粒度）推断"另一端每 200 ms 轮询"，
   分辨不出 1 ms 与 15 ms，这个推断不成立。
2. **补丁改得比 Mac 侧建议的更彻底**：Mac 侧建议的是"队列非空时 1 ms、否则 200 ms"，
   但那仍留一个竞态——若入队发生在「检查队列」之后、`select` 之前，那一行还要等满一轮。
   Windows 侧改成**只要有客户端连接就 1 ms 超时**（空闲无客户端时才 200 ms），把这个缝堵死。
   （`select` 很便宜，最多每秒 1000 次唤醒，CPU 可忽略。）
3. 往返改用 `QueryPerformanceCounter`（亚微秒分辨率），统计行显示到 0.1 ms。
4. 新增**「入队 → 真正发出」耗时统计**（在发送队列旁挂并行时间戳队列，每秒报峰值）——
   这是判断"事件拿到了但发不出去"最直接的指标。

### 第二轮的实测数据

Windows 侧自报（同一台机器）：

| 场景 | 往返延迟 | 发出延迟峰值 | 队列深度 | 发送速率 |
|---|---|---|---|---|
| 静止（仅心跳） | min 5.7 / avg 22.3 / max 77.3 ms | max 0.4 ms | — | — |
| **移动 30 秒（Mac 模式）** | min 4.3 / **avg 13.5** / max 98.6 ms（60 个样本） | max 30 / avg 11.5 ms | max 2 行 | 峰值 156 行/秒，平均 90.5 |

Mac 侧同期（客户端日志 `17:29:31–17:31:20`，即用户画圈期间）：

| 指标 | 实测 |
|---|---|
| 收行速率 | 13.4 – 94.0 行/秒 |
| 注入速率 | 11.4 – 92.0 事件/秒 |
| **往返（客户端自测）** | **3.2 – 18.9 ms，多数 3–7 ms** |
| 单行最长处理 | 0.33 – 0.74 ms |
| 最大收包间隔 | 270 – 1035 ms（见下方说明） |

> **关于「最大收包间隔」这个指标的适用性**：它是"两次 socket 回调之间的最大间隔"。
> 当移动不连续时（用户画圈有停顿），这 5–6 秒窗口里只有每秒一次的心跳，
> 间隔自然会被心跳周期（~700–1000 ms）主导 —— 所以**这个数只有在持续移动时才有意义**，
> 上述 270–1035 ms 反映的是窗口内的停顿，不是卡顿。指标本身需要这样解读，否则会误判。

### 结论

| 对比项 | 第一轮 | 第二轮 |
|---|---|---|
| 两端往返 | 差一个数量级（Mac 10–15 ms vs Windows 0–188 ms） | **吻合**（Mac 3–7 ms、Windows 平均 13.5 ms；残差 ≈ 一个 Wi-Fi 首跳） |
| 用户主观 | 一跳一跳 | **「明显流畅很多」** |
| 定位 | 怀疑客户端 | **确认是服务端发送循环**（Mac 侧代码无需改动） |

剩余抖动来自 **2.4 GHz Wi-Fi**（首跳 avg 7.2 / max 12.4 ms，再加上"路由器 → Windows"这一跳与无线重传），
不是代码问题。可选环境优化：换 5 GHz、或把信道从 1 换成较空闲的 6/11。有线在用户侧不可行。

### ⚠️ 一处设计铁律被推翻（必须记账）

2. 独立看门狗进程兜底（强杀后 200 ms 内解锁，已实测）
3. 记录系统级逃生口（任务管理器会清除别人的 `ClipCursor`）
4. 记录残留风险：看门狗 12 小时上限、点击不被拦截、安全桌面收不到输入

**结论：这条改动可接受，但它把项目从"完全不需要恢复的状态"变成了"持有一个必须恢复的状态"，
因此看门狗、退出清理、以及上面这三条残留风险必须一直在文档里可见。**

## 2026-09-24 · 第三轮：实际使用中暴露的问题

联调通过不等于能用——下面两条都是**用户真正拿它当鼠标用**之后才发现的。

### 问题 1：按住左键拖不动文件（Mac 客户端，已修）

**症状**：用 Windows 鼠标在 Mac 上按住左键拖文件，拖不动。

**原因**：注入器一直发 `kCGEventMouseMoved`。而在**按住某个键移动**时，必须发对应的事件类型：

| 按住的键 | 必须发的事件类型 |
|---|---|
| 无 | `kCGEventMouseMoved` |
| 左键 | `kCGEventLeftMouseDragged` |
| 右键 | `kCGEventRightMouseDragged` |
| 中键 / 侧键 | `kCGEventOtherMouseDragged` |

发错类型时，系统只把它当"光标在移动"，不认为是拖拽 → Finder 拖放、文本拖选、拖动窗口标题栏**全部失效**。

**修法**：`EventInjector.move()` 按当前按住的键选择事件类型与按钮号（注入器本来就记录了哪些键是按着的）。

**为什么之前的验证没发现**：那几轮只覆盖了移动、单击、滚轮，**没有覆盖"按住拖动"这类组合操作**。
教训：KVM 的验收清单里必须有"按住拖动"。

**复测（2026-09-24，用户真机）**：拖文件、拖选文字、拖窗口标题栏 **三条全部正常 ✓** —— 已闭环。

### 问题 2：客户端窗口左上角三个红绿灯点不动（非 bug，属系统行为）

**症状**：用 Windows 鼠标点 MiniKVM Client 窗口的红绿灯按钮，没反应；别的软件却可以。

**三步定位**（均由用户在真机执行）：

| 测试 | 结果 | 含义 |
|---|---|---|
| ① 点窗口**内容区**的按钮（如「清空日志」） | 有反应 | 合成点击能正常到达我们的窗口，链路完整 |
| ② 红绿灯**连点两下** | 第二下生效 | 第一下被吞掉了 |
| ③ 先用真鼠标激活窗口，再用 Windows 鼠标点 | **一下生效** | 被吞的那一下就是"激活窗口"用的 |

**结论**：这是 macOS 的通用行为——**对非当前窗口的第一次点击只用于激活窗口，不会传给按钮**（内容区按钮同理）。
`windows/phase3-tcp/README.md` 里那句"拖动后台窗口标题栏一下就能拖走"也正因如此：标题栏接受 first mouse，按钮不接受。
**不是本项目的问题，记为已知行为**，绕过办法：点两下，或先激活窗口。

**补充澄清（同日）**：用户指出最初抱怨的其实是 **Codex 这个 App 的窗口**，不是 MiniKVM Client 的窗口；
上面①②③三步是在 MiniKVM Client 窗口上做的（三条都符合"激活吞掉第一下"的解释）。
如果 Codex 窗口**当时已经是当前窗口**却仍点不动，那就不再是上面那条系统行为，而更可能是：

> **事件来源不够"真"**。之前所有合成事件都是用 `nil` 作为 `CGEventSource` 创建的（属于私有来源）；
> 带自动化能力的 App 可能读取 `kCGEventSourceStateID` 来识别合成事件并忽略它们。
> **处理**：客户端已改为用 `CGEventSource(stateID: .hidSystemState)` 创建全部事件（鼠标移动/按键/滚轮），
> 让它们在系统看来与真实 HID 事件没有区别。

**待验证**：改用 HID 来源后，在 Codex 窗口上重测红绿灯（一次点击是否生效）。

**最终结论（同日，用户实测）**：**真鼠标也点不动** → 这条症状与 MiniKVM 完全无关，
是 Codex 桌面 App（就是 `/Applications/ChatGPT.app`，bundle id `com.openai.codex`，
内含 `Codex Framework.framework`，原生 macOS App 而非 Electron）那个窗口自身的问题。

- HID 来源那处改动**保留**：它是合成事件的保真度提升（对所有 App 都有益），但**不是**本症状的原因。
- 教训：遇到"某个 App 有问题、别的 App 正常"时，**第一步应当是让对方用真鼠标复现同一操作**。
  如果真鼠标也不行，那就与本项目无关，不该继续在合成事件的实现上找原因。这一轮我们多绕了一步。

**查证（同日，联网检索 `openai/codex` 仓库）**：确认是 **Codex App 自己的已知 bug**，同类 issue 共 35 条，
其中三条证据最完整：

| issue | 状态 | 要点 |
|---|---|---|
| [#34154](https://github.com/openai/codex/issues/34154) | open | **根因**：标题栏的可拖动区域把点击吞掉了。复现步骤与本机现象一致：悬停符号正常出现、单击无反应、**双击黄灯被当成"双击标题栏"导致窗口缩放**、键盘快捷键（`Cmd+W`/`Cmd+M`/`Ctrl+Cmd+F`/`Cmd+Q`）全部正常、跨启动稳定复现 |
| [#29738](https://github.com/openai/codex/issues/29738) | open | **诱因**：App 缩放 **> 100%** 且窗口**最大化**时命中区偏移；原文描述"有时悬停提示只有在指针**不在**按钮正上方时才出现"——与本机观察（放到圆点上方一点才出现图标）一致 |
| [#44457](https://github.com/openai/codex/issues/44457) | closed | 在 Darwin 27.0.0（与本机相同的系统大版本）上报告同一症状；评论称某次更新后"完全点不动" |

本机环境：Codex `26.917.71314` / macOS 27.0（26A428）。

**可尝试的绕过**（按 #29738 的诱因）：把 App 缩放调回 **100%**（`Cmd+0` 或「显示 / View → Actual Size」），
并避免窗口处在**最大化**状态。
**不必重启 Mac**（issue 明确"跨启动稳定复现"），也不必重启 App；真正解决要等官方修复。

**本机实测的缩放阈值（2026-09-24）**：

| App 缩放 | 红绿灯能点吗 | 备注 |
|---|---|---|
| 100% | ✅ 能点 | 但字太小，看得吃力 |
| **140%** | ✅ 能点 | **当前采用**，字大小可接受 |
| 150% | ❌ 点不动 | 命中区偏移，和 #29738 描述一致 |

说明：这是"命中区随缩放逐渐偏移"的典型表现（偏移量累积到超过按钮尺寸时，就完全点不到了），
与 [#34703](https://github.com/openai/codex/issues/34703)「High-DPI 上 100%+ 缩放时按钮顶部被裁掉」同类。
阈值可能随「窗口是否最大化」和「显示器缩放档位」变化；若哪天 140% 又点不动，**先用真鼠标确认一次**，

### ② hidapi 源码分析（`libusb/hidapi`，`mac/hid.c` 1598 行）

macOS 上 `hid_write()` 就是 `set_report(dev, kIOHIDReportTypeOutput, data, length)`，而 `set_report` 的核心是：

```c
report_id = data[0];
if (report_id == 0x0) {          /* 不使用编号报告：不发送报告号 */
    data_to_send = data + 1;
    length_to_send = length - 1;
}
IOHIDDeviceSetReport(dev->device_handle, type, report_id, data_to_send, length_to_send);
return (int) length;             /* 返回值是传入长度，不是实际发出的字节数 */
```

官方头文件亦明确：`data[0]` 必须是 Report ID，单报告设备填 `0x0`，
**"calls to hid_write() will always contain one more byte than the report contains"**。

**结论（直接回答方案 §3 的疑问）**：OpenLinkHub 的 1025 字节**正是** hidapi 需要的长度——
调用 `hid_write(buf, 1025)`、`buf[0] = 0x00`，hidapi 会去掉首字节，设备实际收到 **1024 字节**的报告。
**不需要做任何换算**；"1025 有问题"这个担心来自 hidapitester 的缓冲区上限，不是 hidapi 的限制。
另外：macOS 上 `hid_send_output_report()` 与 `hid_write()` 是同一个实现（等价）。
`hid_enumerate()` 返回的 `struct hid_device_info` 带 `usage_page` / `usage` 字段，方案要求的"按 FF42/01 过滤"用 hidapi 原生即可实现。

**附带核验 hidapitester**（`todbot/hidapitester`，`hidapitester.c` 686 行）：

```c
#define MAX_BUF 1024            /* line 23 */
uint8_t buf[MAX_BUF];           /* line 249 */
res = hid_write(dev, buf, buflen);   /* line 554 */
```

→ "hidapitester 发不了 1025 字节" **成立**；且它没有长度上限保护，传 1025 会越界写栈，**不可用它试**。

### 二、目标接口（0xFF42 / 0x0001）的 Report Descriptor

原文 HEX（29 字节）：

```text
06 42 FF 09 01 A1 01 15 00 26 FF 00 75 08 96 00 04
09 01 81 02 96 00 04 09 01 91 02 C0
```

逐项解析：

| 字节 | 项 | 含义 |
|---|---|---|
| `06 42 FF` | Usage Page (Global) | `0xFF42` |
| `09 01` | Usage (Local) | `0x01` |
| `A1 01` | Collection (Main) | Application |
| `15 00` | Logical Minimum | 0 |
| `26 FF 00` | Logical Maximum | 255 |
| `75 08` | Report Size | **8 bit** |
| `96 00 04` | Report Count | **1024** |
| `09 01` | Usage | `0x01` |
| `81 02` | **Input** (Main) | Data,Var,Abs → **1024 字节输入报告** |
| `96 00 04` | Report Count | **1024** |
| `09 01` | Usage | `0x01` |
| `91 02` | **Output** (Main) | Data,Var,Abs → **1024 字节输出报告** |
| `C0` | End Collection | — |

**关键结论**

```text
Report ID        ：descriptor 里没有 Report ID 项 → Report ID = 0（不使用编号报告）
Output Report    ：Report Size 8 bit × Report Count 1024 = 1024 字节
Input  Report    ：同样 1024 字节
Feature Report   ：无（MaxFeatureReportSize = 0）
Output payload   ：1024 字节
hid_write() 长度 ：1024 + 1（Report ID 字节 0x00）= 1025
```

### 本轮发现并必须记录的一条运行前置条件：**输入监控权限**

现象：`info` 打开设备失败，hidapi 报 `IOHIDDeviceOpen ... (0xE00002E2) (iokit/common) not permitted`。

定位（只读实验）：逐个尝试打开该键盘全部 6 个接口 → **6/6 全部被拒**；
同时 `hid_darwin_get_open_exclusive()` 返回 0，证明"非独占"设置已生效 →
**排除"被其它程序独占"，确认是设备级的系统权限拒绝**。

根因：macOS 自 10.15 起对**键盘类 HID** 的 `IOHIDDeviceOpen()` 施加 TCC 检查，
缺少「输入监控（Input Monitoring / kTCCServiceListenEvent）」时直接失败，**且不弹窗**。
外部佐证：Apple Developer Forums 的 “kIOReturnNotPermitted from IOHIDManager”、
kanata 项目 issue #1037 “MacOS privilege violation error”。

处理：系统设置 → 隐私与安全性 → **输入监控** → 添加实际执行工具的 App（本例为「终端」）→ 退出重开。

**对后续阶段的影响**：MiniKVM 将来若在 Mac 端控制键盘类 HID，同样需要「输入监控」；
它与鼠标注入所需的「辅助功能」是两项不同权限，设计文档里应分开列明。

### 阶段⑩ 方案（第一次真机写入，单次、不重试、不循环）

**当前硬件状态**：键盘用 USB 线连着 Mac（这正是厂商接口可见的前提）；键盘此前与 Mac 配对过蓝牙。

**建议第一个写入命令：`→ BT Host 1`（mode `0x02`）**，理由按风险排序：

| 候选 | 预期后果 | 风险 |
|---|---|---|
| **BT1（0x02）** | 键盘切到蓝牙 Host 1（若 Mac 就是 BT1，键盘仍在 Mac 上）；若"有线优先"，命令被忽略 = 无副作用 | **最低** ✓ |
| SLIPSTREAM（0x01） | 键盘交给 Windows 的接收器 → Mac 立刻失去键盘 | 中 |
| BT2 / BT3（0x03 / 0x08） | 大概率是未配对的主机 → 键盘谁都连不上 | **最高** |

**成功判定分三层（沿用规范 §8）**：

1. `hid_write()` 返回值是否 = 1025（系统是否接受）
2. 设备是否仍可访问（`list` 前后对比、是否重新枚举）
3. 键盘连接模式是否真的改变——用 `tools/k70-watch.py`（监视键盘是否以蓝牙方式连到 Mac）
   加上用户亲手在键盘上打字验证

**恢复手段**：拔掉 USB 线再插回（通常回到有线优先）；必要时用 Windows 侧的键盘/鼠标
（MiniKVM 的鼠标转发仍在，可用鼠标操作 Mac）。

**执行前的确认项（需用户点头）**：

### 结果（`K70-Send-B-Result.txt`）

```text

HidD_SetOutputReport : False
GetLastWin32Error    : 0 (no error)
handle closed
---- after the write ----
```

Mac 侧：21:42:29 键盘在蓝牙上 → 21:44:33 仍在 → 监视器全程没有任何状态变化。

### 判读：这不是"命令被忽略"，而是**写入调用本身被拒**

`HidD_SetOutputReport` 返回 `False`，说明 Windows HID 栈/驱动在这个接口上不接受这次调用
（若真的发出去了而键盘不理，返回值应当是 `True`）。所以本阶段的结论只能到"这一层 API 走不通"。

两个技术点：

1. **错误码 0 是假的**：`[DllImport("hid.dll")]` 漏了 `SetLastError = true`，
   `Marshal.GetLastWin32Error()` 拿到的只是运行时缓存值。已修，下次会给出真实错误码
   （若为 `1 = ERROR_INVALID_FUNCTION`，即"该接口不支持这个 API"）。
2. **hidapi 在 Windows 上根本不是用这个 API 发 output report 的**：它用的是 **`WriteFile()`**
   （`HidD_SetOutputReport` 是另一个入口，`hid_send_output_report` 才用它）。
   同一块接口对两个入口的接受程度可能完全不同 → 下一步换 `WriteFile` 发**完全相同的报文**。

## 2026-09-25 · 阶段⑫-B2：写入被"接受"（这次是真的），键盘**仍然不动** ← 结论基本定案

### 做了什么

用户双击 `K70-B2-切到Windows.bat`（`-Method Both`，报文与 B 完全相同：
`00 08 01 3A 00 01` + 59 个 0 = 65 字节）。Mac 侧两个 `k70-watch.py` 全程在跑。

### 结果（`K70-Send-B2-Result.txt`）

```text
1) HidD_SetOutputReport : True   (Win32 error 0)
...mi_01 still present : True
```

- Mac 侧**又一次没有任何状态变化**：键盘没有离开 Mac，也没有出现在 Windows。
- 与 B 的差异只有返回值（`False` → `True`）——而这个差异**本身是 bug 造成的**：
  `HidD_*` 返回的是 1 字节 `BOOLEAN`，P/Invoke 按默认 4 字节 `bool` 读取会读到高位的垃圾值，
  同一个调用可以随机读成 True 或 False。已修（`[return: MarshalAs(UnmanagedType.U1)]`）。
  也就是说：**两次的返回值都不可信**；可信的是两次都"键盘没动"。

### 结论（结合⑪、⑫-A、⑫-B/B2 四次实测）

**接收器的厂商接口只在键盘以 SLIPSTREAM（2.4G）挂在它身上时才有落点。**
键盘一旦切到蓝牙（本次是 Mac 的 Host 1），2.4G 链路即断，接收器侧的命令没有对象可转发 ——
这与⑪确立的"必须有厂商接口 + 活跃链路才能发命令"完全一致，只是我们原本以为接收器可能例外。

**还剩一个未知量没排除**：接收器路径的端点字节。OpenLinkHub 的 `k70pmW` 用的是**动态查表**的
`d.Endpoint`，而我们沿用键盘直连的 `0x08`。要排除它，只需要一个干净的对照实验：
**先让键盘落到 Windows**（按一次 `Fn+Caps`，此时链路是活的），再由 Windows 发 `→ 蓝牙 Host 1`
（`K70-C-切回Mac.bat`，已改用 `-Method WriteFile` 以便拿到可信的字节数）。
键盘若能跳回 Mac → 通道与 `0x08` 都没问题，上面的结论定案；若仍不动 → 端点字节可疑，
再考虑扫描候选值或读取接收器的输入报告。

### 关于"完全不用按键"的出路（记录，供后续决策）

如果真的要做到**双向都零按键**，可行的形态是"命令 + 让键盘失去 USB"两步：

```text
键盘 USB 线常插在 Mac 上（Mac 始终握有厂商接口）
  Mac → Windows：Mac 发 →SLIPSTREAM（键盘记住无线目标）→ Mac 用软件切断该 USB 口供电
                  → 键盘按记住的目标以 SLIPSTREAM 上线到 Windows
  Windows → Mac：Mac 恢复该 USB 口供电 → 键盘看到 USB 即回到有线（USB 优先）＝回到 Mac
```

需要的硬件只是一个**可软件断电的 USB 口**（Yepkit YKUSH 这类带控制 API 的 USB hub，
或 "USB 继电器模块" 串在键盘线的 VBUS 上，由 Mac 通过串口驱动）。
这条路线不需要任何 `Fn` 组合键，也不受"蓝牙模式下没有落点"的限制 —— 但它需要买一个小硬件。

   继续逆向的收益远小于成本。

**接收器通道到此为止，不再尝试。** 键盘跨机切换的现实选项回到：键盘 `Fn` 组合键，或"可软件断电的 USB 口"硬件方案。

⑪ 那次"插着 USB 线时发命令无效"的判据是"发完 →BT1 之后 Mac 上没有出现蓝牙设备"。但当时发的是

### 2026-09-26 晚 · 抗"网络路径变化"：加 NWPathMonitor（解决 v2rayN 开关/换节点后鼠标卡死）

**现象**：用户在 Mac 上开关 v2rayN（代理）后，Mac 鼠标不动，需要重开 app 才恢复。

**定位**：与"流量被代理"无关 —— 实测到 Windows 是直连（`route get 192.168.1.20` → interface **en1**），
系统代理的 ExceptionsList 里也有 192.168.1.20。真正的原因：v2rayN 开关/换节点会**增删 utun 接口、
重写路由表**＝"网络路径变化"，已建立的 TCP 被打断，`NWConnection` 还可能卡在旧的失败路径上
（与 17:38 那次"一直重连、要重开 app"同源）。

**修复（纯 Mac 侧）**：`MiniKVMClient` 增加 `NWPathMonitor`：
- 监控 `NWPath.status` 与 `availableInterfaces`（接口名集合，能捕捉 utun 的增删）
- 路径变化 → 打印 `[网络] 路径变化（状态…、接口…）` → **立即 `dropConnection()` + `connect()`**，
  不等 3 秒心跳超时、不等 P1 退避（同时把 `offlineSince` 与 `reconnectAttempt` 归零）
- 1 秒去抖，避免路径抖动时反复重连
- 首次回调不动作（只记录基准）

**Windows 侧无需任何修改**（协议/端口/服务端逻辑未动）。

**实测结果（2026-09-26 20:25 之后）**：用户**完全退出 v2rayN** → **鼠标完全没卡** ✓
日志佐证：20:25:32 重连成功后，一直到 20:27 都没有出现 `[网络] 路径变化`、也没有任何 `Windows 端离线`／`连接结束`
→ 说明**退出代理根本没有打断那条局域网连接**（到 Windows 是直连 en1，代理起停不动这条路由）。
结论：之前那次"关代理→鼠标卡死"最可能是**旧版客户端在路径抖动时卡在失败路径/退避过长**；
现在有「NWPathMonitor 路径变化 → 立即重连」兜底，不再需要重开 app。

### 2026-09-27（凌晨）· 根因修复：IP 地址被当主机名解析 → v2rayN 开着就连不上

**现象**：面板显示 `Win（未运行）`，点设置里"未运行"看似没反应；实际日志显示点击**执行了**
（`手动触发重连`），但连接报 `NWError -65554 - NoSuchRecord`（解析失败 ✗），而 Windows 端
`45789` 明明是开放的。

**根因**：`NWConnection(host: NWEndpoint.Host("192.168.1.20"))` 把**IP 字面量当成主机名**去解析，
而 v2rayN（TUN/DNS 劫持）会让这个解析失败 → 连不上。
这解释了此前的"开着代理鼠标就没了 / 重开 app 偶尔又好" —— 解析偶尔通过而已。

**修复**：构造端点时先尝试 `IPv4Address` / `IPv6Address`，命中就直接用 **IP 端点**（`.ipv4/.ipv6`），
完全不进解析器；只有真正的主机名才退回 `NWEndpoint.Host(字符串)`。

**顺带**：设置里点"未运行"现在有可见反馈 —— 6 秒内显示 `重连中…`（橙色），随后按结果回到 已启用/未运行。

## 2026-09-28 · 通用剪贴板兼容性排查（第一轮：**结论是被测环境本身坏了，与 MiniKVM 无关**）

### 起因

用户报告：**iPhone → Mac 的「通用剪贴板」失效，退出 MiniKVM 就恢复**（Mac → iPhone 一直正常）。
据此 ChatGPT 写了一份二分定位规范，要求把 MiniKVM 的功能逐层打开、找出第一个把剪贴板弄坏的模块。

### 为此做的东西（已落地，以后还能用）

| 东西 | 位置 | 说明 |
|---|---|---|
| 调试档位 | `DebugMode`（`src/ui/LinkState.swift`）、`设置 → 兼容性排查` | `空运行 / A 不碰 HID / B 只打开 HID / C HID+读事件 / D HID+读事件+切换 / 完整`，存 `UserDefaults("minikvm.debugMode")`，**重启 app 生效** |
| `--open-only` | `macos/kvm-link/kvm-keywatch.c` | 只 `IOHIDManagerOpen`、不注册回调 → 才测得出"只打开设备"这一档 |
| 定位脚本 | 桌面 `剪贴板排查.command` | 自动切档位、重启 app、打印 app 日志与 keywatch 进程数、把结果写到桌面 |
| 关键修复 | `MiniKVMClient.swift` `willTerminate` | app 退出时**显式收掉 kvm-keywatch 子进程**。原来它会变成孤儿继续持有 IOHIDManager，直接把"不碰 HID"的档位污染掉（当时真查出 2 个孤儿进程） |

### 判定方法的两个坑（都踩过，记下来）

1. **`pbpaste` 看不见通用剪贴板**。通用剪贴板的内容挂在 **remote pasteboard** 上：
   `pboard [com.apple.CFPasteboard:remote] Remote pasteboard fetching local data ...`。
   所以脚本用 `pbpaste` 判定时，**成功也会被判成失败**（v2 整轮结论作废）。
2. **往终端窗口 ⌘V 也拿不到**通用剪贴板内容（v3 六步全 ❌，连基线都 ❌）。
   可靠的判定目标只有普通 App（备忘录/文本编辑），最终改为：**粘进备忘录 + 用 AX 读备忘录正文**。

### 最终实测（MiniKVM **完全退出**、kvm-keywatch **无进程**）

| 次数 | 方向 | 结果 |
|---|---|---|
| 3 次 | iPhone → Mac | **3/3 失败**（粘出来的是本机哨兵 `MAC-OLD-MANUAL-1`） |
| 1 次 | Mac → iPhone | **成功** |

客观佐证：`~/Library/Group Containers/group.com.apple.coreservices.useractivityd/shared-pasteboard/`
里的**远端剪贴板 blob**（`kRemotePasteboardBlobName`）最后一次被写入是 **9月26日 18:30**（262 KB），
而本机 blob 是当天 18:49 —— 也就是说 **Mac 从 9/26 18:30 之后就没再收到过任何远端剪贴板内容**。
今天所有测试都在那之后，所以"MiniKVM 一跑就坏"无法成立。

系统侧检查全部正常：接力开关 `ActivityAdvertisingAllowed/ReceivingAllowed = 1`、
Wi-Fi(en1) 已连、**awdl0 UP+RUNNING**、蓝牙正常、日志里 `ADVERTISING ... UAPasteboardAvailable = 1`
与 `Received a new advertisement` 都在刷。重启 `sharingd`/`useractivityd` **无效**。

### 结论（重启设备后复测）—— **与 MiniKVM 无关**

用户重启 iPhone + Mac 后复测：

| 状态 | 正向（iPhone→Mac） | 反向（Mac→iPhone） |
|---|---|---|
| MiniKVM **未运行**（基线） | ✅ | ✅ |
| MiniKVM **完整档位运行中** | ✅ | ✅ |

客观佐证：重启后 useractivityd 重新生成了两个 blob 文件（UUID 会变），其中
**远端剪贴板 blob**（`0FB396DB-…`，3090 字节）的修改时间是 **19:14:23** ——
而 MiniKVM（完整档位）是 **19:13:11** 启动并在运行的。也就是说：
**MiniKVM 全功能运行时，Mac 确实收到了来自 iPhone 的剪贴板内容**。

**定案**：9/26 18:30 → 9/28 19:07 之间 iPhone→Mac 的失败，是**设备侧接力状态故障**
（重启即恢复），不是 MiniKVM 造成的。在坏基线上跑二分矩阵毫无意义 —— 那一轮的每个 ❌
都不能归因；幸好先验了基线，没有把锅扣在自己程序上。

1. **量 `.icns` 本身**：各档位居中行不透明范围 `x=0..宽度-1`（满幅）→ 圈不是我们画的。
2. **看系统设置**：`defaults read -g AppleIconAppearanceTheme` → **`ClearLight`**（图标与小组件样式＝透明）。
   切到 `Default` 后：我们的**浅蓝底板**立刻显示出来，粗灰圈消失 → 粗圈是"透明"样式的系统重绘。
3. **对照实验**（造一个测试 app，图标是"满幅纯蓝方块 + 白字 TEST"的 `.icns`）：
   在透明档下蓝色被**整块丢掉**，只剩白字被放进系统自己的灰玻璃托盘 → 证明透明档下
   **所有旧格式图标都会被系统剥掉背景、套上系统托盘**，与我们的图标内容无关。
4. 结论：**旧格式 `.icns` 无法去掉那圈**；只有官方新格式（`Assets.car`）才是系统原生渲染。

### 关键技术发现：actool 可以直接编译 `.icon`（不需要 Xcode 工程）

```sh
xcrun actool AppIcon.icon --compile <outdir> --platform macosx \
     --minimum-development-target 26.0 --app-icon AppIcon \
     --output-partial-info-plist <outdir>/icon-partial.plist
# → <outdir>/Assets.car + <outdir>/AppIcon.icns + partial plist(CFBundleIconName=AppIcon)
```

- 依据：`.icon` 在 Xcode 的构建规范里是 `folder.iconcomposer.icon`，
  `BasedOn = folder.abstractassetcatalog` —— 它本身就是一种资源目录。
- **之前失败的原因**：把 `.icon` 塞进 `Assets.xcassets/AppIcon.appiconset/`，
  actool 会把它当**文件**读 → 报 `Is a directory`；放进资源目录顶层则什么都不编。
  正确做法是**把 `.icon` 直接作为 actool 的输入**。

### 落地

- `build.sh`：优先 `actool` 产出 `Assets.car` + `AppIcon.icns` 放进 `Contents/Resources/`，
  失败时回退到 `make-appicon.sh` 预生成的 `.icns`
- `Info.plist`：新增 `CFBundleIconName = AppIcon`（保留 `CFBundleIconFile` 兼容老系统）
- 效果：默认样式下浅蓝底板满幅铺开、**无灰圈**；透明样式下是系统原生玻璃渲染
  （仍会按"透明"档显示成玻璃板，但不再有旧格式那圈托盘边）
