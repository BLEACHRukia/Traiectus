# K70 Pro Mini 键盘跨机切换 · 技术报告

> **历史记录**：本文写于产品名为 MiniKVM 的时期（2026-09-29 正式改名为 **Traiectus**）。
> 正文保留当时的原名/路径，以免记录失真；当前名称与路径见 `README.md`。


**日期**：2026-09-25（全部实验当天完成）
**目的**：判断"不拔线、不按 `Fn` 组合键，纯软件把键盘在 Mac 与 Windows 之间来回切换"在这套硬件上是否可行，并给出确凿证据。
**结论（一句话）**：**在这套硬件上做不到纯软件双向切换**；根本原因是"键盘必须有活跃的命令通道（厂商 HID 接口或经接收器）"与"键盘插线即被该机器独占"这两条同时成立。唯一能实现零按键的形态需要一个小硬件（可软件断电的 USB 口）。

---

## 1. 需求场景（用户侧）

- Mac 是主力机，**平时键盘在 Mac（蓝牙）**上使用。
- Windows 只用来打游戏，**打游戏时必须无线鼠标 + 无线键盘（SLIPSTREAM 2.4G）**，且任何工具都不能影响游戏输入。
- 希望切换键盘时**不拔线、不按键盘上的 `Fn` 组合键**。
- 鼠标跨机共享由 MiniKVM（Windows 转发 → Mac 注入，局域网 TCP）解决；鼠标那只（罗技 GPW2）是"无线接 Windows + 有线接 Mac"的双接法。

## 2. 涉及的硬件与身份（实测）

| 对象 | 身份 | 说明 |
|---|---|---|
| 键盘 USB 直连 | `VID_1B1C` / `PID_1BB6` | Serial `F5XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX`；6 个接口；厂商接口 `usagePage 0xFF42 / usage 0x01` 在 **interface 1** |
| 键盘 USB 直连的 Report Descriptor | 29 字节 | `06 42 FF 09 01 A1 01 15 00 26 FF 00 75 08 96 00 04 09 01 81 02 96 00 04 09 01 91 02 C0`；无 Report ID；Input/Output 各 **1024 字节** |
| 键盘蓝牙 | `VID_1B1C` / `PID_0x1B6E`，Transport = Bluetooth Low Energy | Mac 就是它的 **BT Host 1**（由 `Fn+T` 与 Mac 侧观测双向印证） |
| SLIPSTREAM 接收器 | `VID_1B1C` / `PID_1BA6` | 产品名 **"CORSAIR SLIPSTREAM WIRELESS USB Receiver"**，Serial `A5EF…（序列号已隐去）`；6 个接口 `MI_00..MI_05` |
| 接收器厂商接口 | `MI_01`：`0xFF42/0x01`，**input=65 output=65**；`MI_02`：`0xFF42/0x02`，input=65 output=0 | 即"64 字节报告 + 1 字节 Report ID" |
| 鼠标 | 罗技 GPW2：无线接收器 `VID_046D&PID_C547`（Windows），有线 `PID_C094`（Mac） | 与键盘通道无关 |

## 3. 协议（来自 OpenLinkHub 源码核验 + 真机验证）

命令：`cmdConnectionMode = {0x01, 0x3A}`
报文布局：`[0]=Report ID(0x00)`，`[1]=Endpoint/路由字节`，`[2..3]=01 3A`，`[4]=0x00`，`[5]=mode`，其余补零。

| 目标 | USB 直连（`k70pmWU`，写 1025 字节） | 经接收器（`k70pmW`，写 65 字节） |
|---|---|---|
| 蓝牙 Host 1 | `2` | `2` |
| 蓝牙 Host 2 | `3` | `3` |
| 蓝牙 Host 3 | `8` | `8` |
| **SLIPSTREAM** | **`1`** | **`0`** |

源码证据（`main` 分支，经 `cdn.jsdelivr.net` 获取）：

- `src/devices/devices.go:758` — `7094: {1, 0, "K70 PPO MINI", k70pmWU.Init, nil}`（7094 = 0x1BB6）
- `src/devices/k70pmWU/k70pmWU.go` — `bufferSize = 1024`、`bufferSizeWrite = 1025`、`headerSize = 2`、`bufferW[1] = 0x08`
- `src/devices/k70pmW/k70pmW.go` — `bufferSize = 64`、`bufferSizeWrite = 65`、`transfer()` 中 `bufferW[1] = d.Endpoint`
- `src/devices/slipstream/slipstream.go` — `case 7094:` → `k70pmW.Init(..., value.Endpoint, ...)`；`getDevices()` 中
  `var base byte = 0x08`，`endpoint := base + deviceType`，且 `if channels == 1 { endpoint = base + 1 }`
- **注意**：OpenLinkHub 的接收器表里**没有 `0x1BA6` 这个 PID**（表内是 7039/7041/7078/7132/11008/11035），因此"经接收器"的参数是从别的接收器外推的。

## 4. 实验记录（含原始证据）

### ⑪ 首次成功：USB 直连可以切换（已确立基本机制）

键盘用 USB 线接 Mac，执行一次 `test-bt1`（`00 08 01 3A 00 02`，1025 字节）后**拔掉线**：

```text
hid_write() 返回值 : 1025（期望 1025）      hid_error() :（无错误）
拔线后：Mac 出现蓝牙设备 PID 0x1B6E，用户可在 Mac 打字，Fn+T 指示灯蓝闪
```

→ 确立模型：**命令设置的是"无线目标模式"；插着线时 USB 优先，拔线后键盘才按被命令的模式上线。**

### ⑫-A Windows 只读探测（`K70-Probe.bat`，21:20:37）

```text
product     : CORSAIR SLIPSTREAM WIRELESS USB Receiver
manufacturer: Corsair
serial      : A5EF…（序列号已隐去）
[MI_02] usagePage 0xFF42 / 0x02   input=65  output=0  feature=0
[MI_01] usagePage 0xFF42 / 0x01   input=65  output=65 feature=0
```

同时刻 Mac 侧 `hidutil list`：键盘仅以蓝牙（`0x1B6E`）存在，Mac 上**没有任何 `1b1c` 的 USB 设备**。
→ 判定：Windows 上那个常驻的厂商接口属于**接收器**，与键盘此刻归属无关。
（Report Descriptor 读取返回 `Win32 error 1 / ERROR_INVALID_FUNCTION`，该接口不支持此 IOCTL，不影响构造报文。）

### ⑫-B / ⑫-B2 / ⑫-C：经接收器写入的三次尝试（全部"写成功、键盘不动"）

| 时刻 | 脚本 | 报文 | 结果 | 键盘反应 |
|---|---|---|---|---|
| 21:43:33 | `K70-B` | `00 08 01 3A 00 01`（65B，`HidD_SetOutputReport`） | 返回 `False`，`GetLastWin32Error=0` | 无 |
| 21:47:29 | `K70-B2` | 同上（`HidD_SetOutputReport`） | 返回 `True`，err 0 | 无 |
| 21:54:22 | `K70-C` | `00 08 01 3A 00 02`（65B，`WriteFile`，键盘当时在 Windows） | `True`，bytes written **65** | 无（用户按 `Fn+T` 取回） |
| 22:00 | `K70-B3` | `00 09 01 3A 00 00`（65B，端点改 0x09、模式改 0） | `True`，bytes written **65** | 无 |

**重要技术细节（我们踩过的坑）**：`HidD_*` 返回的是 1 字节 `BOOLEAN`，P/Invoke 若按默认 4 字节 `bool` 读取会读到高位垃圾值，
同一次调用可以随机读成 `True`/`False`（B 与 B2 的差异就是这样来的）。已用 `[return: MarshalAs(UnmanagedType.U1)]` 修正。
`WriteFile` 返回的 `bytes written = 65` 则是可信的：**Windows 确实把 65 字节交给了接收器驱动**。

### ⑫-D 端点扫描（22:06:57–22:07:37）：16 个候选路由字节**全部无效**

键盘先按 `Fn+Caps` 落到 Windows（22:06:54 离开 Mac），随后对 16 个候选路由字节各发**一次** 65 字节报文
`00 <候选> 01 3A 00 02`（模式 2 = 蓝牙 Host 1 = Mac），每次间隔 2.5 秒：

```text
22:06:57.765  0x09  True  65 (err 203)      22:07:17.859  0x00  True  65
22:07:00.267  0x08  True  65                22:07:20.370  0x01  True  65
22:07:02.790  0x0A  True  65                22:07:22.877  0x02  True  65
22:07:05.313  0x0B  True  65                22:07:25.415  0x03  True  65
22:07:07.836  0x0C  True  65                22:07:27.921  0x04  True  65
22:07:10.343  0x0D  True  65                22:07:30.427  0x05  True  65
22:07:12.848  0x0E  True  65                22:07:32.936  0x06  True  65
22:07:15.354  0x0F  True  65                22:07:35.439  0x07  True  65
```

Mac 侧监视器（`tools/k70-watch.py`）：

```text
[22:06:54.303] K70 从蓝牙上消失（键盘已切走）
[22:09:55.083] K70 以蓝牙方式出现   ← 用户按 Fn+T 的结果
```

→ 整段扫描期间键盘毫无反应。**该接收器（PID 1BA6）的厂商接口不执行 `01 3A` 连接模式命令**
（至少在 0x00–0x0F 的路由字节范围内）。可能原因：它只认 iCUE 自己的协议（`slipstream.go` 的读写流程里还有
`cmdCloseEndpoint{0x05,0x01}` → `cmdOpenEndpoint{0x0d,0x00}` → 写 → 读 的四步握手），继续逆向收益远小于成本。

### ⑫-E 关键对照（22:19）：线插 Mac 时发 `→SLIPSTREAM`

**为什么必须做这个对照**：⑪ 判定"USB 优先"时发的是 `→ 蓝牙 Host 1`，**而键盘本来就在 Mac（Mac 就是 BT Host 1）** ——
"没有变化"与"命令没生效"两件事无法区分。正确的对照要指向一个**不同的**目标。

键盘 USB 线插在 Mac 上，执行 Mac 侧 `test-slipstream --confirm`：

```text
目标模式 : SLIPSTREAM（0x01）
目标设备 : 0x1B1C / 0x1BB6，UsagePage 0xFF42，Usage 0x0001，Interface 1
打开     : 成功（non-exclusive）
hid_write() 返回值 : 1025（期望 1025）      hid_error() :（无错误）
发送后：厂商接口数量 1（不变）；蓝牙设备数量 0
```

用户目视结果：**Mac 上可以正常打字，Windows 上没有任何输入。**

→ **有线优先确认**：插着 USB 线时，键盘不会当场切走；命令会被固件"记住"，但要在**失去 USB**之后才生效
（⑪ 已验证"拔线后按记住的目标上线"）。

## 5. 三条通道的可用性总表（结论）

| 键盘状态 | Mac 侧能否发命令 | Windows 侧能否发命令 | 结果 |
|---|---|---|---|
| 键盘在 Mac 蓝牙 | ❌ 蓝牙下不暴露厂商接口（实测：只有标准键盘 HID，`0xFF42` 零命中） | ✅ 有接收器厂商接口 | 接收器**不执行**该命令（16 个路由字节全部无效） |
| 键盘在 Windows SLIPSTREAM | ❌ | ✅ 有接收器厂商接口 | 同上，不执行 |
| 键盘 USB 线插 Mac | ✅ 有厂商接口，1025 字节路径**实测可用** | — | 命令被接受并记住，但 **USB 优先**，当场不变 |
| 键盘 USB 线插 Windows | — | ✅（应同样可用，未实测） | 同"USB 优先" |

**因此：纯软件双向切换在本硬件上不可行。** 键盘插线时才存在可用通道，而插线又把它锁在那台机器上；
无线状态下唯一的通道（Windows 的 SLIPSTREAM 接收器）不认这条命令。

## 6. 可行方案

### 方案 A（零成本，推荐先这样用）

键盘自身的 `Fn` 组合键：`Fn+Caps` = 去 Windows（SLIPSTREAM），`Fn+T` = 回 Mac（蓝牙 Host 1）。
每次切换一次按键，任何状态下都有效。游戏场景不受影响（游戏时键盘本来就在 SLIPSTREAM 上）。

### 方案 B（零按键，需要一个小硬件，原理已被本次实验验证）

把"拔线"这一步换成**软件断电**：

```text
键盘 USB 线常插在 Mac 上（顺便充电；Mac 因此永远握有厂商接口）
  Mac → Windows：Mac 发 →SLIPSTREAM（本次已实测被接受并记住）
                  → 切断该 USB 口的供电（软件控制）
                  → 键盘失去 USB，按记住的目标以 SLIPSTREAM 上线到 Windows ✓
  Windows → Mac：恢复该 USB 口供电
                  → 键盘看到 USB 即回到有线（USB 优先反过来帮忙）✓（今晚已实测：插上线就回 Mac）
```

硬件选项：

- "USB 控制继电器模块"（几十元，串在键盘 USB 线的 VBUS 上，Mac 通过串口/HID 驱动）
- Yepkit YKUSH 这类带控制 API 的 USB hub（更贵但更省事）

Mac 端控制可以做成：双击 / 快捷键 / 跟随 MiniKVM 的模式自动切换。
**这条路线没有任何未经验证的假设**：命令被接受（⑫-E 实测）、断电后的行为（⑪ 用拔线等价验证过）、恢复供电的行为（今晚实测）。

### 方案 C（不推荐）

带物理按钮的 USB 切换器（用户手上已经有一个"转换器"）：能切，但仍需按按钮，且会把 USB 口位占满（本次已遇到"键盘线和鼠标线抢一个口"的问题）。建议顺手买一个 USB hub 解决口位。

- **方案 B 未实测**（缺少可软件断电的 USB 口硬件）。
