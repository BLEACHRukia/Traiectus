# 第 1 篇 · K70_Pro_Mini_HID_测试程序制作方案_给Deep(1).md

# K70 Pro Mini HID 直接控制测试程序制作方案

> **用途：** 把本文档完整交给 Deep，让 Deep 负责制作第一阶段的 macOS K70 Pro Mini Vendor HID 测试工具。
>
> **原则：** 先验证协议和真实 HID 写入链路，成功后再进入 MiniKVM。不要跳步，不要猜包，不要让用户反复执行未经验证的命令。

---

## 1. 项目目标

为 macOS Apple Silicon 制作一个一次性运行的命令行工具：

**K70HIDTest**

用于直接通过 USB HID Vendor Interface 控制：

**CORSAIR K70 RGB PRO MINI SLIPSTREAM WIRELESS**

当前设备信息：

- VID：`0x1B1C`
- PID：`0x1BB6`
- Vendor Usage Page：`0xFF42`
- Vendor Usage：`0x0001`
- Vendor HID：`FF42/01`
- 平台：macOS / Apple Silicon

目标链路：

```text
Mac
 ↓
USB HID Vendor Interface
 ↓
K70 Pro Mini
 ↓
Connection Mode Command
 ↓
Bluetooth Host 1 / Host 2 / Host 3 / SLIPSTREAM
```

第一阶段只做协议验证，不做完整 MiniKVM。

---

# 2. 已确认的协议资料

当前通过 OpenLinkHub 源码确认，K70 Pro Mini `1B1C:1BB6` 使用：

```text
k70pmWU
```

不是 `k70pmW`。

设备注册对应：

```text
VID = 0x1B1C
PID = 0x1BB6
```

Vendor HID：

```text
Usage Page = 0xFF42
Usage = 0x0001
```

Connection Mode command：

```text
01 3A
```

Endpoint/channel：

```text
0x08
```

模式参数：

```text
Bluetooth Host 1 = 0x02
Bluetooth Host 2 = 0x03
Bluetooth Host 3 = 0x08
SLIPSTREAM        = 0x01
```

OpenLinkHub 的传输缓冲结构：

```text
bufferW = 1025 bytes

bufferW[0] = 0x00
bufferW[1] = 0x08

bufferW[2] = 0x01
bufferW[3] = 0x3A
bufferW[4] = 0x00
bufferW[5] = mode

bufferW[6...] = 0x00
```

因此命令前 6 字节：

### Bluetooth Host 1

```text
00 08 01 3A 00 02
```

### Bluetooth Host 2

```text
00 08 01 3A 00 03
```

### Bluetooth Host 3

```text
00 08 01 3A 00 08
```

### SLIPSTREAM

```text
00 08 01 3A 00 01
```

其余部分按照实际 HID Report 要求补零。

---

# 3. 非常重要：不要把 OpenLinkHub 的 buffer 表示法和 macOS HIDAPI 表示法直接混淆

OpenLinkHub 中看到的是：

```text
1025-byte write buffer
```

但 macOS HIDAPI 的：

```text
hid_write()
```

对 Report ID 和 report length 的处理需要根据实际 hidapi 源码、HID Report Descriptor 和真机行为确认。

因此：

**不要简单假定“1025 bytes 一定就是 hid_write() 应该发送的长度”。**

程序必须先读取并分析：

- Report Descriptor
- Output Report Size
- Report Count
- Report ID
- HIDAPI 当前实现

然后计算 macOS 实际应该传给 `hid_write()` 的数据长度。

如果 OpenLinkHub 的第一字节属于 HIDAPI 所需的 Report ID，则明确说明；如果 hidapi 会单独处理 Report ID，则必须正确转换。

# 7. 第一阶段真机测试：BT1 → BT1

用户当前键盘处于 Bluetooth 状态。

如果用户确认当前是 Bluetooth Host 1：

```bash
K70HIDTest test-bt1
```

第一次测试的目的不是切换蓝牙，而是：

> 已经在 BT1 → 再发送 BT1。

因此即使成功，也不会主动把键盘切换到另一个模式。

发送内容应对应：

```text
00 08 01 3A 00 02
```

但最终实际长度必须由程序根据 HIDAPI + Report Descriptor 正确计算。

程序必须：

1. 查找 `1B1C:1BB6`
2. 确认 Usage Page `FF42`
3. 确认 Usage `01`
4. 打开 Vendor HID
5. 打印实际 Report Descriptor
6. 构造 report
7. 打印实际发送长度
8. 打印前 32 bytes
9. 执行一次 `hid_write()`
10. 输出返回值
11. 输出 `hid_error()`（如果有）
12. 等待极短时间观察设备状态
13. 关闭 HID
14. 退出

不要循环。

不要常驻。

---

# 8. 成功判定必须分层

不能看到：

```text
hid_write() succeeded
```

就直接说：

```text
键盘已经切换成功
```

必须区分：

### 第一层

```text
HID write succeeded
```

只能证明 USB HID 写入成功。

### 第二层

```text
Device remained accessible
```

说明设备没有异常。

### 第三层

```text
Keyboard mode change confirmed
```

只有通过可靠的设备状态变化、重新枚举、重新连接或其他可验证机制才能这样说。

如果无法确认实际 mode：

```text
HID command was accepted by the OS/HIDAPI,
but physical mode transition could not be independently confirmed.
```

## 2026-09-25 · 阶段 A：USB 直连后的只读枚举与 Report Descriptor 分析

按《阶段化执行规范 v1.0》§25 执行：键盘用 USB 线直连 Mac，只做枚举 / Usage / descriptor 只读分析，
**不调用 `hid_write()`、不发任何命令**。

### 一、枚举结果：找到 3 个 Corsair HID 接口（同属一个物理设备）

公共属性：

```text
VID          = 0x1B1C (6940)
PID          = 0x1BB6 (7094)
Manufacturer = Corsair
Product      = CORSAIR K70 RGB PRO MINI SLIPSTREAM WIRELESS 60% Mechanical Gaming Keyboard
SerialNumber = F5XXXXXXXXXXXXXXXXXXXXXXXXXXXXXX
Transport    = USB
LocationID   = 0x2110000
```

| # | Usage Page | Usage | RegistryID | MaxInput | MaxOutput | MaxFeature | 结论 |
|---|---|---|---|---|---|---|---|
| 1 | **0xFF42** | **0x0001** | 0x100002163 | 1024 | **1024** | 0 | ★ **目标接口（厂商 HID）** |
| 2 | 0x01 | 0x06 | 0x100002164 | 16 | 2 | 1 | 标准键盘接口（与本次无关） |
| 3 | 0xFF42 | 0x0002 | 0x100002165 | 64 | **0** | 0 | 另一个厂商接口，**只有输入报告、无输出报告** → 不是目标 |

按规范 §9：**目标（VID/PID/FF42/01 四项同时满足）唯一命中第 1 个**；第 3 个虽同为厂商页但 usage 不同、
且没有 Output 报告，已排除并如实列出。

### 二、目标接口（0xFF42 / 0x0001）的 Report Descriptor

原文 HEX（29 字节）：

```text
06 42 FF 09 01 A1 01 15 00 26 FF 00 75 08 96 00 04
09 01 81 02 96 00 04 09 01 91 02 C0
```

逐项解析：

| 字节 | 项 | 含义 |
|---|---|---|
| `06 42 FF` | Usage Page (Global) | `0xFF42` |
| `09 01` | Usage (Local) | `0x01` |
| `A1 01` | Collection (Main) | Application |
| `15 00` | Logical Minimum | 0 |
| `26 FF 00` | Logical Maximum | 255 |
| `75 08` | Report Size | **8 bit** |
| `96 00 04` | Report Count | **1024** |
| `09 01` | Usage | `0x01` |
| `81 02` | **Input** (Main) | Data,Var,Abs → **1024 字节输入报告** |
| `96 00 04` | Report Count | **1024** |
| `09 01` | Usage | `0x01` |
| `91 02` | **Output** (Main) | Data,Var,Abs → **1024 字节输出报告** |
| `C0` | End Collection | — |

**关键结论**

```text
Report ID        ：descriptor 里没有 Report ID 项 → Report ID = 0（不使用编号报告）
Output Report    ：Report Size 8 bit × Report Count 1024 = 1024 字节
Input  Report    ：同样 1024 字节
Feature Report   ：无（MaxFeatureReportSize = 0）
Output payload   ：1024 字节
hid_write() 长度 ：1024 + 1（Report ID 字节 0x00）= 1025
```

### 三、与 OpenLinkHub `k70pmWU` 交叉验证（规范 §12）

| 项 | OpenLinkHub 源码 | 真实 Descriptor | 是否一致 |
|---|---|---|---|
| 写缓冲总长 | `bufferSizeWrite = 1025` | `1024 + 1` | ✅ 一致 |
| 缓冲区大小常量 | `bufferSize = 1024` | Output Report = 1024 字节 | ✅ 一致 |
| Report ID | `bufferW[0] = 0x00`（隐含未编号报告） | 无 Report ID 项 → 0 | ✅ 一致 |
| 首字节之后的端点字节 | `bufferW[1] = 0x08` | 属于 1024 字节报告内容，descriptor 不约束 | — 无从由 descriptor 验证，属协议层约定 |

→ **三项关键结构完全一致**，可以进入"候选真实测试"阶段；但按规范 §25，本阶段**到此停止**，等用户与方案方确认。

### 四、本阶段未做的事

- ❌ 未调用 `hid_write()`、未发送 `01 3A` / `08` / BT1 / BT2 / BT3 / SLIPSTREAM
- ❌ 未做任何自动测试、无循环、无重试、无后台
- ❌ 未写下任何 C++ 代码（`ReportBuilder` 属规范 §13，需 descriptor 验证后才做）
- ✅ 仅使用系统自带只读工具（`hidutil` / `ioreg`）做枚举与 descriptor 读取（规范 §8 允许"等价的只读 HID enumeration"）

```cpp
std::vector<uint8_t> buildConnectionModeReport(uint8_t mode) {

    std::vector<uint8_t> buffer(kWriteBufferLength, 0x00);

}
```

### 1.1 两处方案未提及的发现

**(1) `FF42/01` 无法从 OpenLinkHub 证实。**

## 2. hidapi 源码分析（`libusb/hidapi`，`mac/hid.c` 1598 行）

macOS 上 `hid_write()` 的唯一实现路径：

```c
int HID_API_EXPORT hid_write(hid_device *dev, const unsigned char *data, size_t length)
{
    return set_report(dev, kIOHIDReportTypeOutput, data, length);
}

static int set_report(hid_device *dev, IOHIDReportType type, const unsigned char *data, size_t length)
{
    ...
    report_id = data[0];
    if (report_id == 0x0) {
        /* Not using numbered Reports. Don't send the report number. */
        data_to_send   = data + 1;
        length_to_send = length - 1;
    }
    res = IOHIDDeviceSetReport(dev->device_handle, type, report_id, data_to_send, length_to_send);
    if (res != kIOReturnSuccess) { ... return -1; }
    return (int) length;          /* 返回的是"传入长度"，不是实际发出的字节数 */
}
```

官方头文件（`hidapi.h`）对应说明：

> The first byte of `data[]` must contain the Report ID. For devices which only support a single report, this must be set to 0x0.
> Since the Report ID is mandatory, **calls to hid_write() will always contain one more byte than the report contains.**

**结论（直接回答方案 §3 的疑问）**

- OpenLinkHub 的 **1025 字节正是 hidapi 需要的长度**：调用 `hid_write(buf, 1025)`、`buf[0] = 0x00`，
  hidapi 会去掉首字节，**设备实际收到 1024 字节**的报告。
- **不需要任何换算**。"1025 有问题"这个担心来自另一个工具（见下），不是 hidapi 的限制。
- macOS 上 `hid_send_output_report()` 与 `hid_write()` **是同一个实现**（两者等价）。
- `hid_enumerate()` 返回的 `struct hid_device_info` 带 `usage_page` / `usage` 字段
  → 方案要求的"按 `FF42/01` 过滤"用 hidapi 原生即可实现，不需要额外库。

```text
open_exclusive 全局设置 = 0（0 = 非独占）   ← 我们的设置已生效

[1] iface=2  FF42:02  → 打开失败: (0xE00002E2) not permitted
[2] iface=1  FF42:01  → 打开失败: (0xE00002E2) not permitted
[3] iface=0  1:6 键盘 → 打开失败: (0xE00002E2) not permitted
[4] iface=0  12:1     → 打开失败: (0xE00002E2) not permitted
[5] iface=0  1:2      → 打开失败: (0xE00002E2) not permitted
[6] iface=0  1:1      → 打开失败: (0xE00002E2) not permitted
```

**6/6 全部被拒** → 排除"被其它程序独占"（且非独占设置已生效），是**设备级**的系统拒绝。

## 6. 根因：macOS 的 HID 隐私闸门（需要「输入监控」权限）

- 该 USB 设备整体被系统识别为**键盘类 HID**；macOS 自 10.15 起对键盘类 HID 的
  `IOHIDDeviceOpen()` 施加 TCC 检查，缺少 **输入监控（Input Monitoring / kTCCServiceListenEvent）** 时
  直接返回 `kIOReturnNotPermitted`，**且不会弹出任何提示**。
- 外部佐证（检索到的同类案例）：Apple Developer Forums 的
  “kIOReturnNotPermitted from IOHIDManager”、C++ 程序读键盘被拒的社区帖、
  以及开源键盘映射工具 **kanata** 的 issue #1037 “MacOS privilege violation error”。
- 影响范围：同一台设备上的**所有** interface/collection 都会被拒（含厂商接口），
  与 usage page 是不是 `0xFF42` 无关 —— 我们的实验证实了这一点。

## 4. 本轮发现并必须记录的运行前置条件：**输入监控权限**

**现象**：`info` 首次运行时打开设备失败：

```text
hid_open_path: failed to open IOHIDDevice from mach entry:
(0xE00002E2) (iokit/common) not permitted
```

**定位（只读实验，仅 open/close）**：逐个尝试打开该键盘全部 6 个接口 → **6/6 全部被拒，错误码相同**；
同时 `hid_darwin_get_open_exclusive()` 返回 **0**，证明"非独占打开"设置已生效。
→ **排除"被其它程序独占"，确认是设备级的系统权限拒绝**（与 usage page 是否为 0xFF42 无关）。

**根因**：macOS 自 10.15 起对**键盘类 HID** 的 `IOHIDDeviceOpen()` 施加 TCC 检查，
缺少「输入监控（Input Monitoring / `kTCCServiceListenEvent`）」时直接返回 `kIOReturnNotPermitted`，
**且不会弹出任何提示**。
外部佐证：Apple Developer Forums 的 “kIOReturnNotPermitted from IOHIDManager”、
开源键盘映射工具 kanata 的 issue #1037 “MacOS privilege violation error”。

**处理方式（已生效）**：系统设置 → 隐私与安全性 → **输入监控** → 添加**实际执行工具的 App**
（本例是用户自己的「终端」）→ **完全退出该 App 再重开** → 重跑命令即成功。

**对后续设计的影响（建议写进方案）**：

- Mac 端若要控制**键盘类 HID**，需要 **输入监控** 权限；
- 鼠标注入（CGEvent）需要的是 **辅助功能** 权限；
- 两者是**不同的权限**，将来的 MiniKVM.app 应把这两项分开说明与申请。
