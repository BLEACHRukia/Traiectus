# 验证方案与记录：键盘状态帧规则

更新：2026-09-30

## 0. 一句话

改判定逻辑前后，按这里的三层跑一遍：**离线单元测试 → 合成帧端到端 → 真机按键**。
**前两层不需要碰键盘和显示器**，所以能随时跑、能进 CI。

## 1. 三层验证

| 层 | 需要什么 | 跑什么 | 能证明什么 |
|---|---|---|---|
| ① 离线单元测试 | 只要 `swiftc` | `./tools/frame-rules-test/run.sh` | 判定逻辑本身对不对（纯函数） |
| ② 合成帧端到端 | 只要 app 在运行 | 往 UDP 45790 发一帧 | 收帧 → 记录 → 判定 → 日志 这条链通不通 |
| ③ 真机按键 | 键盘 + 显示器 | `Fn+Caps` / `Fn+T` | 真机帧能被规则认出来；抢跑时序不变 |

### ① 离线单元测试

```bash
./tools/frame-rules-test/run.sh
# 期望：全部通过：57/57
```

覆盖内容：

- 内置 K70 两条默认规则（去 Windows / 回 Mac）
- 不该命中的帧：方向字节是规则外的值、前缀完全不同、帧比规则短
- 畸形输入不崩：`ZZ ZZ`、空串、只有 `KEY`
- `0x` 前缀形式能解析
- `mask` 语义：忽略位生效；mask 长度不对时回落到"全比较"
- 环形缓冲：上限淘汰、未匹配帧去重计数
- **体检结论的六种分支**（结论文案是直接给用户看的，也一并测）：
  两方向都认得出 / 只认去 Windows / 只认回 Mac / 有帧但规则全不认 /
  没切换过要提示重跑 / 完全读不到 → 用不了抢跑；以及"读不到时明细要写清代价（1.7 秒）"
- **从两组样本学规则**（学习向导的核心）：K70 样本学出来 = 内置默认那两条；
  组内会变的字节被掩掉；"规则只保留到最后一个区分位"；两侧相同 / 一侧没帧 / 畸形输入
  三种失败各有具体原因
- **写配置文件不弄丢其它字段**：改过的显示器输入源、默认地址、键盘 VID、未知帧策略都要保留；
  全 `ff` 的掩码故意不写、带忽略位的掩码必须写

加用例的方式：新键盘的帧样本直接往 `tools/frame-rules-test/main.swift` 里加一行 `check(...)`。

### ② 合成帧端到端（不需要键盘）

```bash
# 规则不认的帧 → 只记录 + 提示，不触发切屏
printf 'KEY 11 22 33 44 55 66 77 88' | nc -u -w1 127.0.0.1 45790
printf 'KEY ZZ ZZ'                   | nc -u -w1 127.0.0.1 45790   # 畸形输入
printf 'GARBAGE'                     | nc -u -w1 127.0.0.1 45790   # 应被 KEY 前缀判定挡掉

grep -E "未匹配的状态帧|无法解析的帧" ~/Library/Logs/Traiectus.log | tail -5
```

> ⚠️ **安全约定：合成测试只用"规则不认的帧"。**
> 发一条能命中的帧会**真的执行抢跑**（切屏 + 交鼠标控制权）；Windows 没开的时候，
> 画面会被切到没有信号的输入上。要测命中路径请走第 ③ 层，用真键盘。

判据：同一帧发两次只提示一次（去重生效）；`GARBAGE` 没有任何输出；进程存活。

### ③ 真机按键

1. 按 `Fn+Caps`（去 Windows），等两秒，再按 `Fn+T`（回 Mac）
2. 检查：

```bash
grep -E "未匹配|无法解析|抢跑|屏幕 →" ~/Library/Logs/Traiectus.log | tail -10
```

判据：

- 两个方向都有 `⚡ Windows 抢跑` + `屏幕 → …（m1ddc …，退出码 0）`
- **没有任何"未匹配的状态帧"** —— 出现了就说明真机帧和规则不一致（见第 3 节）

## 2. 启动时就能确认"用的是哪套规则"

```text
[联动] 已启动（检测：kvm-keywatch；抢跑：UDP 45790；状态帧规则：内置默认（K70 Pro Mini））
[配置] …；状态帧规则=内置默认（K70 Pro Mini）；来源：（没有配置文件，全部用默认值）
```

- 配了规则 → `config.json（N 条）`
- 没配 → `内置默认（K70 Pro Mini）`

## 3. 真实案例：掩码写反（2026-09-30，离线测试抓到的）

| | |
|---|---|
| **症状** | `回 Mac` 的帧被判成 `windows`，方向字节是 `03` 的帧也被判成 `windows` —— **所有帧都判成"去 Windows"** |
| **原因** | 规则 `mask` 写成 `ff ff ff ff ff 00`，第 6 字节（**方向字节**）掩码为 `00` = 忽略；于是两条规则命中同一批帧，先列出的那条赢 |
| **怎么发现的** | 离线测试第 1、2 组用例。如果只靠真机测，表现是"抢跑方向全乱"，非常难定位 |
| **修了哪三处** | 内置默认规则、`config.example.json`、`docs/design/…` 文档（新增"掩码陷阱"警示） |
| **结论** | **区分方向的字节，掩码必须是 `ff`** |
