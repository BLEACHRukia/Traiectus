# 键盘状态帧：检测、学习与验证（设计方案）

- 日期：2026-09-30
- 最后更新：2026-10-01（实测与实施结果已并入本文，见 §8 / §11 / §12）
- 状态：**已实现**（2026-10-01 起；唯一没做的是 §5.6 的 `replay` 命令行，文档里标了可选）
- 相关：[`../ARCHITECTURE.md`](../ARCHITECTURE.md)、[`../../PROTOCOL.md`](../../PROTOCOL.md)、[`../devlog/联调记录.md`](../devlog/联调记录.md)

## 0. 一句话目标

让**任何键盘**的用户都能自己把键盘"教"给软件：软件告诉他这把键盘能不能用"抢跑"，
能就学会识别、验证一遍再启用；不能就老实走蓝牙方案，但**功能一样完整**。

## 1. 背景

### 1.1 现在有三处只认 K70 Pro Mini

> 下面是**写方案时（09-30）**的情况。这三处后来都改掉了：桥接脚本退役、判定规则挪进 Mac 侧配置并可由「键盘学习」向导生成（见 §8 第 1 / 3b / 6 步）。

| 只认 K70 的地方 | 位置 |
|---|---|
| `VID 0x1B1C` + `usagePage 0xFF42` + `usage 0x0002` + 报告 65 字节 | 桥接脚本的默认参数 |
| `mode == "02"` → 去 Windows；`== "00"` → 回 Mac | **写死在 Mac 端 `KeyboardLink.readUDP()`** |
| "第 6 个字节就是方向"这个假设 | 同上 |

换一把键盘，任何一处不对，抢跑就不工作 —— 退化到只靠 Mac 侧蓝牙事件（功能仍可用，见 1.3）。

### 1.2 实测结论：抢跑的提前量是**有方向的**

数据来自 `devlog/联调记录.md`，跨机时钟差 0.43 s 已校正：

| 方向 | 抢跑相对 Mac 蓝牙事件的提前量 |
|---|---|
| **去 Windows** | **早 1.56 ~ 1.82 秒** |
| **回 Mac** | **只早 0.13 ~ 0.28 秒 —— 基本没有提前量** |

> ⚠️ 容易搞混的两个数字：**0.38~0.44 秒**是"桥接发出帧 → Mac 完成切屏"的**链路耗时**，
> 不是提前量。凡是提到"快多少"，一律用上表的 1.7 秒 / 0.13~0.28 秒。

"回 Mac 没有提前量"是**硬件天花板**：那个方向上"2.4G 掉线"和"蓝牙重连"几乎同时发生。
旁证：切换时被动的显示器事件监听**一次都没触发**，说明 Mac 侧没有可优化的软件环节。

### 1.3 抢跑与蓝牙是**叠加**的，不是二选一

- 蓝牙方案（`kvm-keywatch` 看键盘设备在 Mac 上出现/消失）**始终在跑**：既是兜底触发，又是**真值**
- 抢跑只是"提前按下按钮"
- 代码依据：`handleHint()`（抢跑）与 `tick()`（归属）并存；抢跑后会同步 `lastActed`，归属事件到达时不会重复动作

所以"读不到状态帧"**不是切换模式，而是"没有加速器"** —— 功能完整，只是"去 Windows"方向慢约 1.7 秒。

## 2. 术语

| 词 | 含义 |
|---|---|
| **状态帧** | 键盘的 2.4G 接收器在"键盘来 / 走"时吐出的 HID 报文，例如 `00 00 01 36 00 02 00 00` |
| **抢跑** | 收到状态帧后，提前把屏幕和鼠标切过去（在键盘真正到达之前） |
| **真值** | Mac 侧 `kvm-keywatch` 判断的键盘实际归属 —— 唯一可信的"到底在哪台机器上" |
| **档位** | 当前使用的检测能力等级（见 3.2） |

## 3. 总体设计

### 3.1 四层 + 第 0 步前提

| 层 | 做什么 | 频率 |
|---|---|---|
| **第 0 步 前提检查** | 确认键盘处于"两台都在线"的状态，否则后面采不到有效样本 | 每次学习前 |
| ① **发现** | 枚举可读的厂商接口（VID / usagePage / usage / 报告长度） | 一次性 |
| ② **采集** | 按提示录两侧样本（"切到 Windows" / "切回 Mac"） | 一次性 |
| ③ **识别** | 自动求差异位 → 生成规则（match + mask） | 一次性 |
| ④ **验证** | 复测打分 + 离线回放 + 运行期自检 | 学习后一次 **+ 每次运行** |

### 3.2 三档能力

| 档 | 信号 | 提前量 | 谁提供 |
|---|---|---|---|
| **1 抢跑** | 接收器状态帧 | **去 Windows 早约 1.7 秒**；回 Mac 无提前量 | Windows（可选加速器） |
| **2 蓝牙** | 键盘在 Mac 上出现/消失（蓝牙/USB） | 0（这是基准线） | Mac（**始终在跑，也是真值**） |
| **3 手动** | 无自动信号 | — | Windows 按 `Ctrl+Alt+M`、显示器 OSD |

**"半抢跑"是常态而不是异常**：天生只有一个方向能抢跑（见 1.2）。向导对此要明确说明。

### 3.3 职责划分

判定与配置**都在 Mac 端**；Windows 端只负责"读帧 + 原样转发"。

| 活儿 | 谁做 | 理由 |
|---|---|---|
| 枚举接口 / 读状态帧 / 转发 | **Windows** | 接收器物理插在 Windows 上 |
| 采集、求差异、生成规则 | **Mac** | 与判定同侧，规则和 `config.json` 放一起 |
| 判定方向（抢跑） | **Mac** | 所有"切不切"的决策本来都在 Mac；以后改进判定算法不用动 Windows |
| 真值（键盘在不在 Mac） | **Mac** | `kvm-keywatch` 现成 |
| 验证与报告 | **Mac** | 用户就坐在 Mac 前面 |

设计上把"帧来源"抽象一层，别写死"一定从 Windows 拿"：

```text
帧来源：① Windows 接收器（主流）   ② Mac 直连的键盘（键盘 USB 插在 Mac 上时）
```

> ② 属于**待验证的扩展口**：已确认 Mac 能看到键盘本体（`1B1C:1BB6`）的 `FF42/01`、`FF42/02`
> 接口，但**键盘本体是否也吐同类状态帧，从没验证过**。数据结构留位置，实现不做。

## 4. 前置改动（必须先做，否则后面看不见东西）

### 4.1 先记录、再判定

现在 Mac 端 `readUDP()` 是**先筛后判**的：前缀不是 `00 00 01 36 00` 的帧直接 `return`，**静默丢弃**。

后果：体检与验证层最想说的那句"**收到了帧、但没匹配到任何规则**"根本看不见。

**改法**：收到任何帧先落进环形缓冲（默认最近 200 条，含未匹配的），再做判定。落盘可选（默认关），出问题时一键导出。

### 4.2 ~~协议加 `KBDSTATE`（客户端 → 服务端）~~ —— ❌ 已取消（2026-10-01）

**不需要做了。** 这条本来是给"判定发生在 Windows 侧"那个版本准备的：真值只有 Mac 有，
所以要跨机送回 Windows 去做对拍。

但设计定型后是反过来的 —— **判定、学习、验证全在 Mac 端**（见 3.3 职责划分），
真值（`kvm-keywatch` 看到键盘在不在 Mac 上）本来就在 Mac 本地，**不用跨机送**。
向导的第 0 步前提检查也因此在 Mac 上直接查，不用问 Windows。

> 保留下面原文作为决策记录。

"键盘此刻在不在 Mac 上"只有 Mac 知道，Windows 看不见。新增一行回报：

```text
KBDSTATE Mac      ← 键盘此刻在 Mac 上（蓝牙或 USB）
KBDSTATE Away     ← 键盘此刻不在 Mac 上
```

- Mac 端在**归属变化时**发，握手完成后立即发一次
- 用途：第 0 步前提检查、验证层的真值对拍、日志
- 老客户端不发 → 服务端按"未知"处理，前提检查明确提示"Mac 端没有回报归属，请升级"

> 这一行同时解决了"验证层要和真值对拍，但判定发生在另一侧"的数据通路问题。

### 4.3 规则配置化

把 1.1 里那三处写死的东西挪进配置（Mac 侧 `config.json`）。

## 5. 详细流程

### 5.1 第 0 步：前提检查

| 检查 | 判据 | 不满足怎么办 |
|---|---|---|
| ① 接收器在 Windows 上 | 能枚举到候选厂商接口 | 把 2.4G 接收器插到**这台** Windows 上（别插扩展坞、别插别的机器） |
| ② 键盘连在 Mac 上 | **本地**：`kvm-keywatch` 看到键盘在 Mac 上（原设计想用跨机的 `KBDSTATE`，已取消） | 在 Mac 上按 `Fn+T`，让键盘回到蓝牙 |
| ③ Mac 端 Traiectus 在线 | TCP 握手完成 | 先启动 Mac 端 |

三条都 ✓ 才允许进入采集。

**为什么这三条是硬前提**：采样靠"接收器吐帧"；"回 Mac"方向的有效样本必须有蓝牙侧；真值要从 Mac 送过来。

### 5.2 一键体检（发现层 + 读不到的处理）

跑 15 秒，让用户随意切两次，直接给结论：

```text
[1/2] 请随意切换键盘两次（切到 Windows 再切回来）
      采集 15 秒…   收到 4 帧（接口 FF42/02）

[2/2] 结论：✓ 这把键盘支持抢跑 —— 接着学规则就行
```

读不到时：

```text
[2/2] 结论：✗ 读不到可用的状态帧

      仍然能用：走蓝牙方案。
        · 去 Windows：比支持抢跑的键盘慢约 1.7 秒
        · 回 Mac：    本来就一样快（该方向没有提前量）
      功能完全一样。

      想再确认一次可以试：
        · 把接收器换到另一个 USB 口（有些扩展坞/HUB 会挡掉厂商接口）
        · 确认插的是接收器、不是键盘本体
```

### 5.3 采集 → 生成规则

按提示各录一次，自动求"两侧恒定、且彼此不同"的字节 → 生成 `match + mask`。

真机上 K70 的样本就是：

```text
去 Windows：00 00 01 36 00 02 00 00
回 Mac   ：00 00 01 36 00 00 00 00
→ 差异在第 6 字节；前 6 个字节全部参与比对（不写 mask，或 mask = ff ff ff ff ff ff）
```

**这条正好是验收判据**：向导对 K70 跑一遍，产出的规则应当与现在写死在代码里的等价。

> ⚠️ **掩码陷阱（实现时真踩到过，被离线测试抓到）**：`mask` 里 `00` 表示"这个字节不比较"。
> 区分方向的那个字节掩码必须是 `ff` —— 第一版把它写成了 `00`（`ff ff ff ff ff 00`），
> 等于忽略了方向字节，于是两条规则命中同一批帧、所有帧都被判成"去 Windows"。
> 学习向导自动求 mask 时，必须保证"区分位"落在 `ff` 上。

采不到规则时（不是"读不到帧"，是"读到了但学不出"）要给具体方向：

| 情况 | 提示 |
|---|---|
| 两次样本**完全相同** | 可能选错接口（比如选到 `FF42/01` 而不是 `FF42/02`） |
| 一次切换吐**多帧**、方向不唯一 | 建议再录一次；或手写规则（支持多条 match） |
| 操作太快 | "每次切完等 1 秒再点下一步" |
| 始终失败 | 允许**导出原始帧全量**，直接贴 issue |

### 5.4 复测打分（验证层 a）

规则生成后立刻让用户切 3 次，**按方向分开报**（否则"回 Mac 没命中"会被误认为失败）：

```text
复测结果：
  · 去 Windows：3/3 命中抢跑（提前约 1.7 秒）              ✓
  · 回 Mac    ：未匹配 → 该方向本来就没有提前量，走蓝牙方案 （正常）
```

### 5.5 运行期自检与档位（验证层 b）

**有帧但一直不命中**最容易让人以为软件坏了，必须显式说出来：

- 计数：最近 N 次键盘归属变化中命中帧的次数（例：10 分钟 3 次切换、0 次命中）
- 触发：日志 + 设置面板状态改为「**仅蓝牙**」
- **规则保留不动** —— 一旦又收到匹配帧，自动回到「抢跑」，不用重启

**判定与真值不一致**时（只可能发生在"去 Windows"方向）：

- 日志打 `⚠ 抢跑方向与实际归属不一致`
- 存一份报告（见 7.2），用户可直接贴 issue
- 最近 200 条帧里把这一段一并带上

### 5.6 离线回放（验证层 c，给 CI 与排查用）

样本落成 JSONL，用现有规则回放，检查判定结果 —— 这是**唯一保留命令行形态**的功能：

```text
traiectus-ctl replay samples.jsonl rules.json
```

好处：规则逻辑有自动化测试，将来能进 CI。

## 6. 交互形态（选定：A）

**向导做进设置面板**（`设置 → 键盘` 一页），不是命令行。理由：用户就坐在 Mac 前面按键盘，提示应该出现在他眼前。

页面结构：

```text
键盘
├─ 当前检测方式：  抢跑（提前约 1.7 秒）    ●      ← 三档，实时状态
├─ 键盘：          Corsair K70 Pro Mini（VID 0x1B1C）  ← 从配置读
├─ 规则：          2 条（去 Windows / 回 Mac）  [查看]
├─ [ 键盘向导 ]      ← 打开向导（前提检查 → 体检 → 采集 → 复测）
├─ [ 重新验证 ]      ← 用现有规则跑一遍复测
└─ [ 导出诊断报告 ]  ← 报告 + 最近 200 条帧，贴 issue 用
```

向导本身是分步面板（不是一次性对话框），每步都能"上一步"；采集步骤要有明显的"现在请按 Fn+Caps"提示和倒计时。

## 7. 数据格式

### 7.1 规则（写进 Mac 侧 `config.json` 的 `keyboard.detect`）

```json
{
  "keyboard": {
    "detect": {
      "interfaces": [
        { "vid": "0x1B1C", "usagePage": "0xFF42", "usage": "0x0002", "reportBytes": 65 }
      ],
      "rules": [
        { "match": "00 00 01 36 00 02",
          "side": "windows", "note": "K70 Pro Mini：去 SLIPSTREAM" },
        { "match": "00 00 01 36 00 00",
          "side": "mac",     "note": "K70 Pro Mini：回蓝牙" }
      ],
      "unknownFramePolicy": "log"
    }
  }
}
```

`mask` 为 `00` 的字节不参与比较（省略则全都比）—— 学习向导的实质就是**自动算出这个 mask**。
上面两条故意不写 mask：K70 的前 6 个字节都是恒定的，第 6 个就是方向位，全比才对。

### 7.2 诊断报告（`keyboard-verify.json`）

```json
{
  "when": "2026-09-30T12:04:11+08:00",
  "keyboard": { "vid": "0x1B1C", "interface": "FF42/02", "reportBytes": 65 },
  "detectionMode": "preempt",
  "samples": [
    { "t": "12:03:58.221", "frame": "00 00 01 36 00 02 00 00",
      "verdict": "windows", "truth": "away", "ok": true }
  ],
  "summary": { "correct": 2, "wrong": 0, "unmatched": 0 },
  "recentFrames": ["最近 200 条，含未匹配的帧"]
}
```

## 10. 验收判据（对着 K70 跑）

### 设备事实

接收器 = **`VID_1B1C` / `PID_1BA6`**，暴露 4 个 HID 接口，其中两个是厂商接口：

| 接口 | 路径片段 | usagePage | usage | in | out |
|---|---|---|---|---|---|
| **FF42/02**（桥接读的那个） | `mi_02` | 0xFF42 | 0x0002 | 65 | **0** |
| FF42/01 | `mi_01` | 0xFF42 | 0x0001 | 65 | 65 |

> ⚠️ **订正任务单里的一处错误**：我写的期望是"两个厂商接口都是 `in=65 out=65`" —— **错了**。
> `FF42/02` 实际是 **`out=0`**（只有输入报文）。对只读的我们来说正合适。
> 记在这里，免得以后有人照着我那句错的期望去比对。

### 帧（和桥接日志在同一时刻对照）


前 6 字节完全一致 → **自己读和桥接读拿到的是同一份数据**。

### 对 3b 有用的三个细节

1. **不独占**：两个句柄同时读同一接口，各自都拿到完整报文（见 9.2）→ 迁移期可以先并存观察
2. **`DevicePath` 会变**：`mi_02#7&20ca56af&0&0000` 这段随 USB 口/集线器变化 →
   服务端启动时**按 usagePage/usage 重新枚举**，不要写死路径（桥接现在就是这么做的）
3. **可以更严谨**：探测工具用的是 `GENERIC_READ|GENERIC_WRITE`（在 `out=0` 的接口上也打开成功了）；
   正式实现可以只请求 `GENERIC_READ`，更贴合"只读"的定位

## 12. 3b 实测结果（2026-10-01，Windows 侧）

**已完成，PowerShell 桥接退役。** 三条职责都并进了服务端：

| # | 原桥接职责 | 服务端现在怎么做的 |
|---|---|---|
| 1 | 读帧 → UDP `KEY …` 发 Mac 的 45790 | 读线程按 VID + usagePage + usage **重新枚举**，`GENERIC_READ` 打开，阻塞 `ReadFile`，取前 8 字节转大写十六进制 → `KEY …`，**`sendto` 直发 UDP** |
| 2 | 每 2 秒发 `HB` 维持回程 | **同一个 socket** 上每 2 秒发一次（首次立即发） |
| 3 | 把 Mac 发到 45790 的包中继到 127.0.0.1:45791 | **其实从来不需要**：控制权切换走的是 **TCP 协议行 `MODE`**（实测确认）；仍在同一 socket 上收 UDP 当保险 |

> ✅ **任务单有一句写错了，他们处理对了**：我在 §3.2 写"投进服务端已有的发送队列"。
> 那条队列是 **TCP** 的，而 Mac 的抢跑是监听 **UDP 45790** —— 放进 TCP 队列 Mac 根本收不到。
> 他们按"转发格式与桥接一致、Mac 零改动"这个更高优先级处理，直接用 `sendto` 发 UDP ✓。
>
> 顺带纠正一个早期架构误解：**Mac 的 UDP 回包从来不需要中继**（职责 3 多余），
> 因为控制权一直是 TCP 进来的。
